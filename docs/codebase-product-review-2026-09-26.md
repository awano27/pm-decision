# kimeru コードレビューと製品改善提案

- レビュー実施日: 2026-09-26（JST）
- 文書化日: 2026-09-27（JST）
- 対象: ローカル `main`、HEAD `e1aad68`。レビュー時と文書化開始前の作業ツリーはクリーンで、`origin/main` より2コミット先。
- 方法: コード・テスト・文書の読み取り、ローカルのオフライン試験、Microsoft 公式資料の確認。実テナント、実 Teams 画面、Kev の実推論、外部送信は未検証。

## 総評

判断グラフ、重大事象をモデルより先に扱う規則、判断経路の記録は、PM の判断を支援する製品のよい土台になっている。一方、外部システムへのアクションは現在 `planned` として記録する MVP であり、無人常用に必要な重大判定・送信内容の照合・イベント再処理・評価方法には修正が必要である。

`python -m unittest` は88件成功し、`python -m kimeru validate` は同梱の8 playbook・4 graphで成功した。これらは実テナントでの取得・通知・承認・外部アクションの成功を示すものではない。

本書の優先度は、**P1: 無人常用や安全性の説明より前に対処**、**P2: 限定導入または機能拡張前に対処**を意味する。

## P1: コードと評価の重要指摘

### 1. ADO の重大チケットが固定 P1 判定を迂回できる

[`match_node`](../kimeru/graph.py#L126) は、`title` と `description` のどちらかに除外語があれば、両方の重大パターン判定を取り消す。[ADO グラフ](../graphs/ado_workitem.json#L142) は「テスト環境」などを除外語にしている。

`title=本番で全ユーザーがログインできない`、`description=テスト環境での再現手順を追記` では固定 P1 規則を通らない。後段に模擬的な低いモデル回答を与えると、P3 に到達することを確認した。これは実モデルが P3 と回答した証拠ではなく、「重大事象はモデルに任せない」という規則の保証に穴があることの再現である。

**対応:** 一致と除外を同じフィールド、可能なら同じ文脈で評価する。本番影響とテスト環境への言及が混在した場合は除外で下げず、人の確認へ送る。この入力を回帰テストに追加する。

### 2. Teams 送信前に予定本文と入力欄の全文を照合していない

[`teams-self.ps1`](../tools/teams-self.ps1#L253) は入力欄を空にせず貼り付け、送信前には先頭が `[kimeru` かだけを確認する。以前の下書きが残る場合、新文を追記した本文や古い本文を送信し得る。[`notify.py`](../kimeru/notify.py#L111) は返された `typed` を確認せず、送信済みとして記録する。

**対応:** 入力欄が空でなければ中止し、貼り付け後に全文を予定本文と比較する。送信後も投稿 ID または投稿本文を確認してから `posted=True` にする。これは静的レビューの指摘であり、実 Teams では再現していない。

### 3. E2E 評価が確認待ちと行動の正しさを過大計上し得る

[`eval/e2e.py`](../eval/e2e.py#L98) は `advise` 終端を一律「人に回した」と数える。しかし、アラートグラフの [`tune_rule`](../graphs/monitor_alert.json#L138) は `queue:false` で、実際には確認待ちにならない。模擬的な誤答では必要な予防対応をせず `tune_rule` に進んでも、評価は `human`、重大な取りこぼしは `false` になった。

同じ評価器は[終端ノード名だけ](../eval/e2e.py#L100)で正解を判定する。違う playbook を選び、予定タスクが変わっても、同じ終端に着けば正解となる。これは実 Kev の誤答を示したものではなく、採点器の誤分類可能性を示すオフライン再現である。

**対応:** `needs_human` と実際のキュー登録を基準に「人へ」を判定する。終端に加えて playbook、必須アクション、優先度、期限を採点する。重大アクションが欠けた例は必ず失敗に数える。

### 4. 一時障害後にイベントが自動処理対象から外れる

[`daily.process_inbox`](../kimeru/daily.py#L31) は、判断時例外を原則 `done/*.error` に移す。受信箱に残すのは、例外文に `not reachable` が含まれる場合だけである。[バックエンド](../kimeru/backends.py#L48)の HTTP 429・5xx は再試行後に別の文面で失敗するため、サーバーが復旧しても自動再処理されない。

また、[`process`](../kimeru/cli.py#L49) は判断を1件ずつ追記し、イベント ID による処理済み判定をしない。同じサンプル入力を2回処理すると `decisions.jsonl` が2行になることを確認した。複数項目を含む入力が途中で失敗すると、一部だけ記録され、残りを含むファイルが `.error` に移り得る。

**対応:** 再試行可能な障害を例外型と HTTP 状態で区別し、上限付き再試行と手動再投入を用意する。入力イベント ID とグラフ版をキーに処理を冪等化する。必須工程が失敗した `daily --once` は終了コードまたはヘルス状態にも反映する。

### 5. アラート取得窓と Teams 取得範囲に欠落リスクがある

[Azure アラート取得](../kimeru/pull.py#L151) は `timeRange=1h` 固定である。1時間を超える停止後には取得窓外のアラートを拾えないおそれがある。Microsoft の [Alerts Get All API](https://learn.microsoft.com/en-us/rest/api/alerts-management/alerts/alerts/get-all?view=rest-alerts-management-alerts-2019-03-01) も `timeRange` を取得結果のフィルターとして定義している。実テナントでの欠落は今回確認していない。

[Teams 取込](../kimeru/pull.py#L177) は画面上のチャット一覧にある**最後のプレビューと時刻の差分**であり、全文や全着信の監視ではない。初回に表示済みのチャットは既定で取り込まない。最小化中の新着反映、職場テナント、UI 更新への耐性は [PoC 文書](teams-uia-poc.md#L22) でも未検証とされている。

**対応:** アラートは前回成功時刻から重複を許して取得し、ID で重複排除する。Teams では取得できた範囲、最終観測時刻、画面取得失敗を見えるようにする。職場テナントで新着・最小化・UI 更新時の受入試験を行う。

## 評価数値の扱い

[README の Kev 評価値](../README.md#L80)は架空イベントを対象とする。現行の調整用フィクスチャは99件・175ラベル・97リクエストで、[評価 README](../eval/README.md#L29)の「197問」と一致しない。ホールドアウト36件の内訳は Teams 20、ADO 8、議事録 8で、監視アラートは0件である。保存済み Kev 回答が現ツリーにないため、62/25/12/0、29/6/0/1、中央値3.6秒は今回再計算していない。

また、[`run_eval.py`](../eval/run_eval.py#L150)の `live --backend kev` は直後の採点に既定の Jev しきい値を使い、[欠損回答](../eval/run_eval.py#L123)は警告なく分母から除く。モデル別 profile、回答件数、フィクスチャ版を記録し直してから数値を製品説明に使うべきである。

## 製品改善の順序

最初の価値検証は、**1プロジェクトの ADO 新規チケット一次整理**に絞ることを提案する。ADO にはタイトル、説明、受入条件、既存 ID があり、現状の Teams プレビューより入力範囲を定義しやすい。まず「重大候補の提示」「情報不足の指摘」「次に確認すべきこと」を PM に示し、承認後の処理結果まで追跡する。この選定はコードからの推論であり、利用者インタビューによる価値の確認は別途必要である。

1. **信頼性を固める。** P1 を修正し、重複・欠落・誤送信・重大取りこぼしの回帰試験を加える。採点器を修正して性能値を測り直す。
2. **PM が判断できる画面にする。** 元情報、規則またはモデルの経路、確信度、予定アクションの全文、現在の状態を1件ごとに示す。`OK N` はどの版のどの本文を承認したかまで記録する。
3. **連携を段階的に広げる。** Teams 全文が必要なら Microsoft Graph の委任 `Chat.Read` を実テナントで検討する。公式資料では権限自体に管理者同意は必須ではないが、テナントの同意ポリシーとアプリ登録可否は別途確認する。[チャット取得 API](https://learn.microsoft.com/en-us/graph/api/chat-list-messages?view=graph-rest-1.0)、[権限一覧](https://learn.microsoft.com/en-us/graph/permissions-reference)。ADO Service Hook は公開 HTTPS 受信先とプロジェクト側の権限が必要なため、会社 PC だけで動かす構成ではポーリングも選択肢として残す。[Azure DevOps Webhooks](https://learn.microsoft.com/en-us/azure/devops/service-hooks/services/webhooks?view=azure-devops)
4. **効果を測る。** 正答率だけでなく、重大事象の見逃し、確認キューへの到達率、重複件数、取込漏れ、PM の採用率、実行完了までの時間を追う。「人に回した」は `advise` に着いた件数ではなく、実際に通知され、PM が確認できた件数で測る。

## 現時点の判断と検証境界

デモと限定的な読み取り試験を進める土台はある。無人の定期運転や「重大事象を確実に拾う」という説明は、P1 の修正と実テナントの受入結果がそろってからにすべきである。

Jev は判断補助として使用し、重大判定の迂回・送信照合漏れ・評価器の見逃しを高リスクと分類した。Jev の判定を実装権限や実行結果の証拠には用いていない。
