## 実データでの評価の手順（ローカルだけ）

ネットワーク・実モデル・有料の呼び出しは、この手順の準備（1〜4）では使いません。データはリポジトリの外（状態フォルダ）に置きます。

1. `kimeru review` で正誤を付ける（状態フォルダの `fixtures_user.jsonl` に、ラベル付きの例がたまります）
2. `kimeru dataset anonymize` で **匿名化の候補** を作る。元のファイルは変更しません。メール・URL・電話番号・ADO の番号・@メンション・作成者欄の名前・GUID・IP アドレス・長い数字・トークンらしい文字列を、同じ値には同じ置き換え（`<PERSON_1>` など）で置きます。社名・製品名などを追加で置き換えるときは `--terms <1 行 1 語のファイル>` を使います
3. 出力の `review_PRIVATE.txt`（置換の一覧と、残るリスクの箇所）を読み、`candidate.jsonl` を直す。この一覧は元の値を含むので、共有せず、確認後に削除してください。**自由記述の欄の秘密情報・固有名詞は残ることがあります**
4. 確認できたら `kimeru dataset mark-reviewed <フォルダ> --i-reviewed`。それまで状態は `candidate`（`human_review_required`）のままです。確認は、その時点の内容のハッシュに対して記録され、あとで内容が変わると無効になります。確認済みでも「匿名化済み」とは扱いません
5. `kimeru dataset split <フォルダ>` で、調整用（tune）と評価用（eval）に分ける。行の id のハッシュで決まり、何度実行しても同じです。欠けた項目・今のグラフで採点できない行・重複・同じイベントへの異なるラベルは、理由付きで除外します。ほぼ同じ文面の行は同じ側に入れます。データ版（ファイルのハッシュ）とグラフの fingerprint を記録します
6. `python eval/dataset_eval.py run --dataset <フォルダ> --backend kev` で eval 側を採点する（`eval/e2e.py` と同じ採点）。結果には、データ版・グラフの fingerprint・モデルの識別子・採点方法を記録し、正しい行動 / 人の確認へ / 安全側の代替行動 / 誤った行動 / 重大な取りこぼし / 判定できない を分けて数えます。条件が合わない結果は `PROVENANCE_MISMATCH` として、数字を出しません
7. `python eval/dataset_eval.py status --dataset <フォルダ> --result <結果>` で、現在のグラフ・採点実装との一致も確認します。`kimeru dataset status` はデータ・結果・現在のグラフを照合しますが、採点実装は未照合として、ロードマップを DONE にしません。採点実装との照合にはこちらの評価用コマンドを使ってください

評価用のグラフ fingerprint は、しきい値と進め方の型も含めます。旧 fingerprint のデータセットや、これらを変更した場合は split し直してください。校正用の fingerprint（しきい値を除外するもの）とは別です。

結果はリポジトリ外の新しいファイルへ保存します。既存の入力・結果は上書きしません。同じデータを再評価するときは `--out <新しい結果ファイル>` を指定してください。入力なしの評価は `NO_INPUT` と終了コード 1 を返し、成功として扱いません。データの欠損・改変・行数の不一致は、評価結果がまだない場合も `PROVENANCE_MISMATCH` です。

## 文面の質

下書きは「安全」だけでなく「そのまま使えるか」を測っています（`python eval/draft_quality.py --writer copilot --show`）。
日本語で書かれているか・英語のままの文がないか・定型文の言い換えで終わっていないか・不自然な言い回し（「発火」など）や、材料にない権限者・完了の言及がないか・材料の具体的な言葉を使っているか・材料にない日付や数値がないか、を機械的に数えます。
書き方の決まり（種別ごとの構成、良い例・悪い例）をプロンプトに入れ、読みづらい文面は、直す点を具体的に伝えて **1 回だけ** 書き直させます（CLI の writer のみ）。

文脈（前例・直前のやり取りなど）を writer に渡す設定の効果は、`eval/draft_quality.py --settings a=b` で同じ fixtures を設定の組ごとに回して比べます（下書きごとの事実照合率と、依頼文に入ったブロックを記録します）。PM の修正率は、状態フォルダに対して `eval/revision_rate.py --out <フォルダ>` で writer ごとに数えます。測り方と、固定の台本 writer で依頼文の組み立てだけを確かめた結果は `eval/README.md` にあります。実際の writer での効果は未測定です。

以下は過去の測定（履歴）で、現行版の文面の質として扱わないでください。架空の 12 イベント（Copilot CLI）で、決まりを入れる前は 76%、入れたあとは 94〜97% でした（LLM の揺れがあります）。別の 8 イベントでは 86%（英語の用語が残る例）。
これは作者の作ったチェックと小さな標本での数字で、**あなたが「そのまま送れる」と感じる割合ではありません**。実際の業務のメッセージで、`修正 N` の回数を見ながら調整してください。
