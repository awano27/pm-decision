# 承認した ADO コメントを実行する

既定では、承認（`OK N`）は「計画を記録する」だけです。ADO へのコメントだけ、承認のあとに kimeru が書けます（`daily` と `approvals` の経路だけ）。

## 有効にする

```powershell
python -m kimeru config set ado_org "<組織>"
python -m kimeru config set ado_project "<プロジェクト>"
python -m kimeru config set execute ado.comment
```

- `execute` に書けるのは、実装済みの `ado.comment` だけです。ほかの種類（`ado.update` など）を書くと、「未対応」と表示され、これまでどおり記録のみです。
- 認証は、あなた自身の `az` のサインイン（`az login`）です。トークンは記録も表示もしません。
- 元に戻す: `python -m kimeru config unset execute`

## 動き

1. コメントを書く判断は、**自動で決まったものも、承認待ちに回ります**（有効にした種類は、承認なしでは動きません）。
2. 承認の投稿に、**書かれる文面のすべて（末尾の 1 行も含む）** と、書き先（作業項目と、その作業項目の取り込み元の組織・プロジェクト）が出ます。この文面と書き先は、**投稿のときに確定して保存**します。投稿のあとに設定（署名の有無など）を変えても、書かれる文面は、投稿に表示したものと一字一句同じです。
3. `OK N` の返信で、その文面が **そのまま** 書かれます（末尾に、「kimeru が下書きし、本人が承認した文面です」の 1 行が付きます。グラフの定型文のときは「kimeru の定型文を、本人が承認した文面です」の 1 行で、文末の「— kimeru」は外します。`config set execute_signature 0` で外せますが、変えたあとに投稿された分から効きます）。付帯の項目（下書きの印など）は送りません。
4. 結果が自分とのチャットに返ります: 「[kimeru 実行 #N k] 実行しました。作業項目 7002 にコメント」／「実行できませんでした（書けていません）。理由」／「書けたかどうか分かりません。ADO を確かめてください」（k はその件の何回目の結果か。やり直せる結果には、末尾に、もう一度やり直すための返信 `「再実行 N-k」` が書いてあります）。すべての実行は `executions.jsonl` に残ります（日時、承認の番号、キー、種類、対象、組織、プロジェクト、状態。「実行中」も残ります）。
5. 結果の投稿は、`--send` を付けた実行（`daily --send`、`approvals --send`）のときだけ送ります。付けないときは貼り付けだけで、送信待ちとして残り、次の `--send` のときに送ります。投稿に失敗したときも、次のサイクルで送り直します。

## 書き先の確認

- `pull ado`（`daily` の取り込み）は、作業項目を取り込んだ組織とプロジェクトをイベントに記録します。実行のときに、これが設定（`ado_org` / `ado_project`）と一致しなければ、**書かずに**知らせます。
- 取り込み元が記録されていないもの（サービスフックで届いたもの、記録を始める前に取り込んだものなど）は、書き先を確かめられないので、書きません。承認の投稿の時点で「書きません（取り込み元が記録されていない）」と出ます。`OK N` は記録だけで終わり、失敗にも「再実行」の対象にもならず、閉じる操作も要りません（そのために Teams を読みに行くこともありません）。
- 実行の記録（`executions.jsonl`）の `running` / `done` / `failed` / `unknown` / `closed` / `skipped` のすべての行に、組織とプロジェクトが入ります。
- 実行を有効にする**前**に投稿された確認待ちは、`OK N` でも書きません。書く文面と書き先を示して投稿し直すので、確かめて、もう一度 `OK N` と返信してください。

## 実行されない経路

実行するのは、`daily` と `approvals`（と、その前段の `notify`）の経路だけです。次は、設定に `execute` があっても、**実行しません**（記録のみ）。

- `demo`（デモ）
- `eval\` の評価のスクリプト（`day_run.py` など）
- `run`、`watch`

## 2 回書かない

- 実行の前に「実行中」を保存し、実行のあとに結果を保存します。
- **失敗**（書けていないことが確か。権限・入力の誤りなど）: 承認は残ります。直したら、結果の投稿に書いてある `再実行 N-k`（または `再実行 N`）と返信すると、もう一度実行します。
- **結果が分からない**（応答のタイムアウト、切断、502〜504、書き込みのあとの記録の失敗、実行の途中で止まった）: 書けている可能性があるので、**自動では書き直しません**。次の手順です。

### 結果が分からないとき

1. 「書けたかどうか分かりません。ADO を確かめてください」という投稿が来ます（1 回だけ）。
2. ADO で、その作業項目を開いて、kimeru のコメントがあるか見ます。
3. **あった**: `済 N` と返信します。その件は閉じられ、その件のために Teams を読みに行くことはなくなります。
4. **無かった**: `再実行 N` と返信します。kimeru は、書く前に、同じ文面のコメントがすでにないか ADO を読んで確かめます（コメントは**すべてのページ**を読みます。ADO へ送るコメントは `<` と `&` をエスケープして、平文として表示される形にします。比べるときは、承認した文の側ではタグを除かず（エスケープの解決と空白の畳み込みだけ）、ADO が保存した側ではタグの除去、エスケープの解決、空白の畳み込みの順に掛けるので、`<b>` や `List<String>`、`件数 < 3` が、実体参照（`&lt;`）だけで保存されていても、タグで包まれて保存されていても（`<div>件数 &lt; 3</div>`）一致します。`A<X または Y>D` と `A<B または C>D` は一致しません。あれば書かずに、書かれていたことを返します。確かめられなければ書きません。確かめられなかったときは、状態は「分からない」のままで、「確かめられませんでした」と知らせます（`済 N` は効き続けます。もう一度確かめるなら、あらためて `再実行 N` と返信します）。承認した文に実体参照（`&lt;`、`&copy`、セミコロンの無い `&not` など）があると、解決したあとの文が同じになる別のコメントを「すでにある」と見なして書かないことがあります（旧版からの限界です）。
5. `再実行 N` は、返信 1 通につき 1 回だけ効きます（番号が使い回されたときも、同じです）。同じ返信が画面に残っていても、次のサイクルで実行し直しません。もう一度実行したいときは、あらためて返信してください。結果の投稿の 1 行目は `[kimeru 実行 #N k]` で、k はその件の何回目の結果かを表します（k の無い古い投稿は 0 回目として扱います）。返信が新しいかどうかは、画面に出ている投稿や返信の数ではなく、「その返信より前に、何回目までの結果の投稿が見えているか」で決めます。見える結果の回数は、その番号の最後の承認の投稿（`[kimeru #N]`）より後ろにあるものだけを数えます（上に残る前の件の結果は数えません）。最後に効いた再実行のあとに出た結果（それより大きい k）の後ろにある返信が、新しい返信です。承認の投稿が画面の上に流れて見えなくても効きます。同じ内容の行が続くと、Teams の画面の読み取りは 1 行にまとめるので、結果の投稿を待ってから、あらためて返信してください。
6. **結果の投稿に書いてある返信 `再実行 N-k`（例: 1 回目の結果なら `再実行 1-1`）** は、画面に何が見えていても効きます。k がその件の最新の結果の回数と一致するときだけ、1 回だけ実行します。最新でない回数の返信（すでに新しい結果が出たあとの `再実行 1-1`）は実行せず、無視したことを `approvals.log.jsonl`（`redo_ignored`）に、無視した返信にだけ、回数ごとに 1 回残します。効いた返信は、あとで次の結果が出ても、無視とは記録しません。最新より大きい回数（まだ無い結果の回数）の返信は、いったん「回数が大きすぎる」として `redo_ahead` を 1 回だけ記録し（PC の通知は、古い回数の「無視: 古い回数」とは別の文言です）、あとでその回数の結果が出て、最新の回数が追いついたときに、1 回だけ効きます（結果の投稿の「再実行 N-k と返信」の案内のとおりです。二重に書くことは、同じ文面の確認が防ぎます）。番号と回数の間の区切りは、`-`（ハイフン）のほか、`ー`（長音符）`−`（U+2212）`‐`（U+2010）`‑`（U+2011）`‒`（U+2012）`–`（U+2013）`—`（U+2014）`―`（U+2015）`─`（U+2500）`ｰ`（半角の長音符）`－`（全角）も読みます。`〜` や `/` など、読めない区切りの形（空白だけの `再実行 1 2`、`1一2`、`1_2`、`1ー` のように回数が続かない形も含みます。`再実行 1 お願い` のような文は含みません）は、形の種類ごとに 1 回（同じ件でも、別の形が来れば、また）`redo_malformed` と記録して、PC の通知に「再実行（形が違います）」と出します（返信の文字は残さず、形は短いハッシュだけを残します）。番号だけの `再実行 N` は、上の 5 の規則のままです。
7. **効かない返信が 2 つあります（利用者には何も出ません）。** (a) 結果の投稿より前（上）に並んだ返信。実行している間、投稿が待ち行列（outbox）に残っている間、`--send` なしの `approvals` で貼り付けだけをしている間に送った返信は、結果の投稿の上にあるので、効きません。(b) 結果の投稿が他の投稿で画面の外へ流れたあとに送った、番号だけの `再実行 N`。起点が見えないので効きません。流れてしまったときは、`再実行 N-k` と返信してください（k は、状態フォルダの `approvals.json` のその件の `x_seq`（最新の結果の回数）か、結果の投稿の 1 行目 `[kimeru 実行 #N k]` の k で確かめます。`executions.jsonl` には回数の欄が無く、`running` の行も混ざり、「分からない」を知らせる投稿は行を作らないので、そこでは数えられません）。

8. 旧版が残した件（旧版で再実行が効いたあとに更新した件など）は、更新後の最初の新しい返信が効きます。更新をまたいだ件は、最大 1 回、旧版より多く再実行することがありますが、再実行の前に同じ文面がすでにないか ADO で確かめるので、二重には書きません。

**試験の投稿の印**: `tools\check.ps1` の試験（番号は T5 が 100〜998、ほかが 100〜898 の乱数）が自分とのチャットに書く投稿は、本番とは別の印 `[kimeru 試験 #N]`（結果の投稿は `[kimeru 試験 実行 #N k]`）で始まります。定期の `daily` と `approvals` は、この印の投稿を承認の投稿とも区切りとも読まず、その下に続く返信（`OK N`・`NG N`・`再実行 N`・`再実行 N-k` など、どの形でも）も、試験の返信として読み捨てるので、番号が `daily` の件と重なっても、その件の承認や再実行には当たりません。試験の側は、自分の印の投稿と、その下の返信だけを読みます（iPhone の返信は、試験の投稿より下に打ってください）。試験の間も `daily` を止めなくて構いません。

### 同時に動かない

承認の記録（approvals.json）を読んで書く処理は、すべて同じロック（状態フォルダの `approvals.lock`）の中で、同時に 1 つだけ動きます（承認の読み取りと実行、確認待ちの投稿、通知の記録、全文の期限切れの削除、続きのメッセージの取り込み）。定期の自動運転と、手で打った `approvals` が重なったときは、あとのほうは何もしません（承認と実行の記録を消さず、同じ OK を 2 回書かないため）。手で打った `approvals` と `notify` は「another approvals run is in progress」と出し、何もせず、終了コード 1 で終わります。定期の自動運転は、その回のレポートの `busy` に載せて、次のサイクルでやり直します（`schedule status` に、飛ばしたステップが出ます）。少し待って、打ち直します。ロックのファイルを作れない（フォルダに書けない）ときは、「busy」ではなく「cannot create the lock file …: the folder cannot be written to」と出ます。その場合は、フォルダの権限と空き容量を直します（待っても直りません）。手で打った `notify` と `approvals` は、何もせずに終了コード 1 で止まります。定期の `daily` は止まりません。ロックが要るステップだけがエラーとしてレポートに載り、取り込み、判断、朝のまとめ、サイクルの記録は続きます。続きのメッセージは、前の件に足さず別の件になります（`warnings.jsonl` に記録します。受信ファイルは `.error` に回りません）。全文を保存する鍵を作れないとき（`read_full=1` や writer を使う構成）も、受信ファイルは `.error` に回らず、その件は全文を保存せずプレビューだけで判断して投稿し（投稿に「プレビューだけで判断しました」と出ます）、`warnings.jsonl` に `save failed` と残ります。次のサイクルへは回しません。受信箱のフォルダが無く、作れないときも、サイクルは止まらず、`waiting` と `judge` のステップだけがエラーとしてレポートに載ります。ロックのファイル（`--out` で指したフォルダの `approvals.lock`。全文用は `full_text.lock`）には、持ち主のプロセス番号と作成時刻が書いてあります。同じプロセスが生きているロックは、古くても（30 分を超えても）引き継ぎません。終わっているプロセスのロックと、同じ番号を別のプロセスが使っている（作成時刻が違う）ロックは、すぐに引き継ぎます。Windows が開くことを拒む（アクセス拒否の）プロセスの番号が書かれたロックも、kimeru のプロセスではないので、すぐに引き継ぎます（番号が使い回されたものです）。解放に失敗して残ったロックは、同じプロセスが次に取るときに引き継ぎます。動いている kimeru が無いのに取れないときは、そのフォルダのロックのファイルを手で削除します。

**全文の削除に失敗したとき**: 全文の削除（承認・却下のあとの削除、7 日の期限切れの削除）は、(1) ファイルを消せない、(2) 置き換えに失敗する（別のプロセスが開いたまま）、(3) 読めない、のどれでも、成功とせず、`warnings.jsonl` に「delete failed」と記録します（読めないときは、何も消しません）。失敗しても、確認待ちの投稿は止まらず、承認・却下と実行、同じ回の他の件の処理と `approvals.log.jsonl` の行も欠けません。残った全文は、次のサイクルの期限切れの削除が、承認・却下の済んだ件のものも含めて、成功するまでやり直します。`warnings.jsonl` への記録は、同じ失敗につき 1 サイクルに 1 行で、大きくなったら新しい 200 行ほどに刈り込みます。想定外の例外も記録します。続いている間は、`daily` のレポート（`full_text_delete_failed`）と `schedule status` に、消せなかった件数が出ます。

**状態フォルダは 1 つの Windows アカウントだけで使います**: ロックの持ち主を調べる処理は、Windows が開くことを拒むプロセスを kimeru ではないと見なします（kimeru は起動した利用者の権限で動くため）。別の Windows アカウントが同じ状態フォルダで kimeru を動かすと、その生きたロックが奪われます。アカウントごとにフォルダを分けてください。

### 1 つの失敗が他に響かない

- 1 つの失敗が、同じサイクルの他の承認の保存を妨げません。

## 相手への返信

`teams.reply` / `teams.post` は、送りません。承認すると、**送る文面だけ** の投稿（`[kimeru 送信用 #N]`）が自分とのチャットに返ります。iPhone で長押しして、コピーして送ってください。
`config set open_chat_link 1` にすると、相手とのチャットを開くリンクが付きます（実験的。リンクに文面は入りません）。

## 試験（管理された PC）

試験用の作業項目（誰の邪魔にもならないもの）を用意して、次を実行します。

```powershell
.\run-check.cmd T22
```

作業項目の番号を入力すると、承認の流れを 1 回通し、コメントが **1 回だけ** 書かれたかを確かめます。試験用の作業項目（誰の邪魔にもならないもの）で、次も確かめてください。

- 結果が分からないときの手順: 試験のあと、`executions.jsonl` の状態が `done` であることと、ADO のコメントが 1 件であることを見ます。もし `unknown`（結果不明）になったら、ADO を見て、`済 N` か `再実行 N` を返信し、コメントが 2 件にならないことを確かめます。
- 組織やプロジェクトを、設定と違うものにした作業項目で、書かれないことを確かめます。

## 試験で確かめること（実機）

- `<` を含む文面（`check.ps1` の T22 は「件数 < 3」「<b>」と改行を入れます）で、ADO がコメントをタグで包んで保存するか、`<` をエスケープして保存するかと、`再実行 N` の確認がその形と一致したかを、真偽だけで結果シートに出します（同じ文面を 2 回書かないこと）。
- 同じ作業項目に、コメントが多数ある（ADO の 1 ページを超える）場合にも、同じ文面を見つけること。
