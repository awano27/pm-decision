# リファレンス

コマンド・設定・環境変数・出力ファイル・入力形式・判断グラフの書き方・評価の実行方法です。概要は [README](../README.md) を見てください。ここの `kimeru …` は、clone したフォルダで実行する `python -m kimeru …` の略です（`pip install git+https://github.com/awano27/pm-decision` または `uv tool install` で入れたときは、そのまま `kimeru …` です）。

### コマンド

- 判断の正誤を付ける・週の集計・係数の調整: `kimeru review` / `kimeru digest --week [--share]` / `kimeru calibrate [--apply | --revert | --allow-wider]` / `kimeru replay` / `kimeru learn list | revert L<n>` / `kimeru config show --share`（[下の節](#判断の正誤の確認と係数の調整)、[1 週間の試し方](trial-week.md)）

```bash
python -m kimeru validate
python -m kimeru try [--out <フォルダ>]              # 体験モード: 架空の相談 1 件を届く→整理→修正→承認→記録まで。設定・鍵を読まず、プロセスの起動と通信を止め、out/try にだけ書く
python -m kimeru demo [--pace 1.5] [--fresh]       # 既定の出力先は out/demo。デモ以外の記録があるフォルダでは止まる（--fresh で before-demo-<日時>/ へ移す）
python -m kimeru run <payload.json>...
python -m kimeru watch inbox/                     # inbox/*.json と議事録 *.txt を常駐処理（処理済みは inbox/done/）
python -m kimeru digest                           # 今日の判断件数と確認待ち
python -m kimeru memory <N>                        # #N と同じ相手・チャット・作業項目・規則の前例と経緯（読むだけ。`KIMERU_MEMORY` の 0/1 によらず表示）
python -m kimeru owed                              # 返事の借り: 自分が返事をまだ返していない件と、閉じた件の内訳（`KIMERU_SENT_WATCH=1` のときだけ。読むだけ）
python -m kimeru pull teams|ado|alerts --inbox inbox    # ado: --org <組織 or URL> [--project <名前>] [--login]
python -m kimeru brief [--post [--send]]
python -m kimeru daily [--once] [--send]
python -m kimeru schedule install|remove|status   # タスクスケジューラ（管理者権限不要）（remove は install が保存した設定も戻す。`--keep-settings` で戻さない）
python -m kimeru push test|status                 # 通知の経路（iPhone 用）の試験と状態（[docs](push-notification.md)）
python -m kimeru notify [--send]                   # 確認待ちを自分とのチャットへ（--send なしは貼り付けだけ）
python -m kimeru approvals                         # 自分とのチャットの返信（OK / NG / 保留 / 詳細 / 修正 / 聞き返し / 再実行 / 済）を読む
python -m kimeru report [--html <ファイル>]        # --out の判断を 1 枚の HTML に（既定 <out>/report.html）
python -m kimeru retry                             # inbox/done/*.error を inbox へ戻す（原因を直してから）
python -m kimeru review | digest --week [--share] | calibrate   # 下の節を参照
python -m kimeru work list|set ... / delivery list|retry|confirm|reconcile ...   # 下の「手動の進捗と曖昧な配信の確認」
python -m kimeru onboarding ... / trial ... / requirements ...         # 1 週間の試し方（trial-week.md）と要件ドラフト（下の節）
python -m kimeru config show|set|unset|path [--share]                  # 設定（下の「設定ファイル」）
python -m kimeru diagnose [--write <ファイル>] [--no-probe] [--drive]   # 配信結果不明・判断の経路・サイクルの失敗を数だけで 1 枚に（run-diagnose.cmd。何も送らない）
```

#### 手動の進捗と曖昧な配信の確認

`--out` はトップレベルのコマンドより前に指定します。`work` は明示承認済み case の作業進捗をローカルに記録します。`STATE` は `approved` / `in_progress` / `done` / `blocked` です。`done` は人が手動で付ける進捗で、case の承認状態、ADO の状態、外部実行を変更しません。

```powershell
python -m kimeru --out <出力先> work list
python -m kimeru --out <出力先> work set N STATE [--owner TEXT] [--due YYYY-MM-DD] [--completion-condition TEXT]
```

配信結果が曖昧で自動再送を止めているときは、`delivery list` で本文を表示せず対象を確認し、必要なら `show` で保留中の本文をローカルに表示します。`KIND` は `case` / `notice` / `outbox` / `brief`、`TARGET` は case 番号・通知キー・`outbox`・`brief` です。

```powershell
python -m kimeru --out <出力先> delivery list
python -m kimeru --out <出力先> delivery show KIND TARGET
python -m kimeru --out <出力先> delivery retry KIND TARGET --confirm-not-sent
python -m kimeru --out <出力先> delivery confirm KIND TARGET --confirm-delivered
```

配信結果が不明の件が多いときは、1 件ずつ確かめずに `delivery reconcile`（`run-fix-deliveries.cmd` をダブルクリックでも同じ）を使います。質問せず、何も送りません。自分とのチャットを 1 回だけ読み（`diagnose` と同じ読み取り専用の読み方）、送ろうとした本文が見えるかを、送信時の読み返しと同じ規則（空白を無視・手前の短い飾りと後ろの短い時刻を許す・URL の前のリンクの読み上げ名を除く・`[kimeru` で始まること）で調べます。

- 見えた: `confirm` と同じ（確認済み）。
- 見えない: `retry` と同じ（次のサイクルで送り直す）。ただし 24 時間より古い件は送り直さず閉じる。case は確認待ちのまま投稿済み扱いにし（承認にはしない）、朝のまとめに出る。通知と outbox の古い件は捨てる。
- 朝のまとめ: 見えなければ保留を解き、新しい朝のまとめが出る（昨日のものは送り直さない）。
- 送ろうとした本文の記録が無い件は、新しければそのまま、古ければ閉じる。

出力は種類・番号・判定だけで、本文・題名は出ません。`kimeru-fix-deliveries-result.txt`（git 管理外）に書き、Google ドライブに `kimeru-release` フォルダがあればそこへもコピーします。approvals.lock を他の実行が使っているとき、Teams を読めないときは、何も変えずに止まります。記録は `delivery-recovery.log.jsonl` に `source: reconcile` で残ります。

`retry` は「送られていない」と確認した場合だけ `--confirm-not-sent` を付けます。これは自動再試行の保留を解除するだけで、その場で送信しません。`confirm` は、期待された本文全体が自分とのチャットに表示されたという本人の申告を `user_confirmation` として記録し、保留を解除します。画面の読み戻しによる確認とは区別され、case の承認、作業の完了、ADO 実行を意味しません。どちらも確認フラグを省けば状態を変更しません。古い改訂の不明結果を確認しても、新しい改訂を投稿済みにはしません。配信の確認記録はその時の申告または読み戻しの証拠として残し、実際の相手側の処理完了とは区別してください。

### Teams の本文を全文で読む

既定では、チャット一覧の 1 行のプレビューだけを読みます。長い依頼は途中で切れ、その前のやり取りも見ません。`kimeru config set read_full 1` にすると、**必要な件だけ**、そのチャットを開いて直近のメッセージ（既定 5 件）を読みます（読み取りだけ。入力欄には触りません）。

- 開くのは、①プレビューが途中で切れている（末尾が「…」。設定 `preview_cut_len` に長さを入れると、その長さ以上も切れているとみなします。既定 0 = 記号だけ）とき、②プレビューでの判断が、人の確認か通知になるとき、のどちらかだけです。ただの挨拶や、自動で決まって通知の要らない件は開きません。プレビューが `read_min_preview`（既定 12。12 より小さくはできません）字より短い件は、開いたチャットが正しいか確かめられないので、開かずにプレビューで判断します
- 全文を読むかどうかを先に決めてから、writer の下書きを **1 回だけ** 書きます（判断は、プレビューと全文の 2 回になることがあります）
- 1 サイクルに開く件数（`read_max_open`、既定 3）と時間（`read_budget_sec`、既定 60 秒）に上限があります。超えた分は、次のサイクルに回します（失敗としては数えず、`schedule status` に「次のサイクルに残したファイル」として別に出ます）。次のサイクルは、プレビューでの判断をやり直さず、読む所から続けます（下書きは、読んだあとに 1 回）。どちらかを 0 にすると、読まずに、プレビューで判断します（待たせません）。人の操作と重なって回した件は、最初に回したときから 24 時間、`read_max_defer`（既定 12）回まで回し、超えたらプレビューで判断します。`read_max_defer=0` は「延期しない」で、最初の 1 回は読み、そのとき読めなければ（操作中、Teams が使用中、件数や時間の上限）、次のサイクルに回さず、プレビューで判断します（読まない設定ではありません）
- 開いたことは、**一覧が選択を報告する画面では、一覧の選択の状態と画面の題名の両方** で確かめます。**選択を報告しない画面では、題名だけでは足りず**、読んだ文がプレビュー（先頭 40 文字）と合うことも確かめます（プレビューが 12 文字未満なら、どの画面でも開きません。「名前:」または「名前：」（空白は有っても無くても）を外したあとの本文で数えます）。選択を報告しない画面で、開いているチャットの題名が読むチャットの題名と同じとき（開いたかの判定と同じ照合です）は、画面を動かさず、何も読まず、プレビューで判断します（何も操作していないので、自分とのチャットへ移さず、通知もせず、延期にも数えません）。確かめられない、または読んだ内容がプレビューと合わないときは、何も使わず、プレビューで判断します（承認の投稿と記録に「プレビューだけで判断しました」と出ます）
- 読み終えたとき・読めなかったとき・途中で失敗したときの、どの場合も、元に開いていたチャットへ戻します（元のチャットは、一覧の選択と画面の題名の両方で覚えます）。時間切れや、操作の確認の例外でも、自分とのチャットへ移す処理を通ります。戻せなければ自分とのチャットへ移し、それもできなければ PC に通知します（`KIMERU_TOAST=0` や通知に失敗したときは、自分とのチャットへ「[kimeru 通知]」として投稿します）。何も動かしていないときは、「開いたままの可能性」とは知らせません。戻れたかどうかは、判断の結果に関係なく、記録（`read_full.returned`・`restore`）に残り、戻せなかった件は投稿と朝のまとめに出ます
- **開く前に、読み取りだけで確かめます**: キーボード・マウスが `read_idle_sec`（既定 30 秒。`idle_sec` は読む処理に影響せず、`idle_sec=0` でも 30 秒です）止まっていること、Teams のウィンドウ（ポップアウトしたチャットを含む）が前面にないこと、Teams の入力欄（Edit / Document）にフォーカスがないこと（フォーカスの場所が取れないときは、使用中として扱います）。どれかに当たれば、何も開かずに次のサイクルに回します。開いたあとも、画面を操作する直前ごとに `read_idle_sec` で確かめます。元のチャットへ戻す処理だけは、別に短く（3 秒の無操作、待ちは最長 20 秒。`read_idle_sec` が 3 未満ならそれに合わせます）確かめます。読む途中であなたが作業を再開しても、同僚のチャットを開いたまま残さないためです。チャットの画面へページを切り替えたとき（Activity・Calendar から）も操作とみなし、戻せなかった件は「戻せなかった」と報告します。Teams を前面に出してクリックする経路は、既定では使いません（`read_click=1` のときだけ）。固定のリンクで Teams が前面に出たときも、終わったあと、元の前面のウィンドウへ戻します
- **開いたチャットは、Teams で既読になります。** 開いて読んで「対応は不要」だった件は、朝のまとめに、件数とチャットの名前で出ます（未読の印を失って見落とさないため）
- 判断モデルには、`text` を `judge_text_max`（既定 1200 文字）で切って渡します。全文は、writer の材料と、承認の投稿の「元（全文）」に使います。直前のやり取りは、writer だけが見ます（判断モデルには渡しません。例外: 設定 `judge_context=1` のとき、この PC の Kev・CLM だけは、同じチャットの直前のメッセージの 120 字までの抜粋（72 時間以内の新しい順 2 件）と今日の日付を見ます）
- 全文を保存するのは、**確認待ちの間だけ**（`out/full_text.json`）。承認か却下のあとは消え、記録に残るのは、これまでと同じ長さの要約です。確認待ちや未投稿のままの件も、`full_text_keep_days`（既定 7 日）で消え、その件は、プレビューだけで判断したものとして扱います。消せなかったとき（別のプロセスが開いているなど）は残り、次のサイクルでやり直します（失敗が続く間は、`daily` のレポートの `full_text_delete_failed` と `schedule status` に件数が出て、`warnings.jsonl` に同じ失敗を 1 サイクル 1 行で残します）。全文を保存できないとき（保存の鍵を作れないなど）は、受信ファイルを `.error` に回さず、その件をプレビューだけで判断して投稿します。全文は `.jsonl` に書きません（m365 の依頼文も、記録には抜粋で作ったものを残し、全文のものは `full_text.json` に置きます）
- 同じチャットの続きのメッセージは、前の件がまだ確認待ちなら、同じ番号の投稿に「続きのメッセージ」として加わります。同じ人のお礼・了解・あいさつ・絵文字だけ（規則 `ack_only` の文）は、「続きのメッセージ」の 1 行（120 字まで、最新 20 件まで）に足すだけで、投稿し直しも判断もせず、件の内容・改訂・保留や承認の状態・全文は変えません（既定で有効。これまでは、件の内容を消して投稿し直し、保留も待ちに戻していました）
- 行動の題名（ADO の題名など）は、1 行で、`title_max`（既定 100 文字）までです
- 実機での確認: `run-check.cmd T23`（プレビューの長さの分布だけを記録。`preview_cut_len` の目安も出ます）、`T24`（既読のチャット 1 件を開いて読み、元へ戻れるか、読んだ文がプレビューと合ったか、選択を報告する画面か）。T24 は、読んだあとに「N 秒以内に Teams の入力欄をクリックしてください」と出して待ち（既定 8 秒。`KIMERU_T24_FOCUS_SEC` で 3〜60 秒）、そのあとで `diag` を取ります（ポップアウトした窓を確かめるときは、その窓を前面にして、その入力欄をクリックします）。結果シートの `T24-diag` には、フォーカスの種類（type）、topPid、fgPid、それぞれが Teams のプロセスか、`teamsInUse` を、数字と真偽だけで出します（本文は出しません）。NG のときも、スクリプトの生の出力は結果シートに書きません

### 判断の速さ

- `decisions.jsonl` の `perf` に、1 イベントごとの **判断の呼び出しの回数・質問の数・秒数・writer の秒数** を残します。サイクルごとの合計は `daily.log.jsonl` に、中央値と最大は `kimeru digest`（と `digest --week`）に出ます
- 判断の順番は、設定 `priority`（既定 `monitor.alert,teams.chat,ado.workitem.created,meeting.item`）。1 サイクルの時間の上限は、設定 `cycle_budget_sec`（既定は自動運転の間隔）
- 設定 `plan_lean=1` にすると、進め方（plan）は、不要と判断した手順の期限を聞きません（既定は無効: 呼び出しが増えるため。速くなるかは Kev で測ってから決めます）。最終的な行動は変わりません
- 設定 `batch_questions=1` にすると、グラフの judge の質問を **1 回の呼び出し** にまとめます（既定は無効。規則だけで決まる経路は、どちらでも 0 問）。最終的な行動は、判断モデルが質問を互いに独立に答えるなら、1 問ずつと同じです
- `batch_questions=1` のとき、規則の結果で通らない枝の質問は、聞きません（規則で外れた質問まで聞くと、質問が増えるため）
- 設定 `split_asks=1` のとき、2 件以上の依頼がある Teams のチャットは、依頼ごとに判断します（R35）。組み合わせは `kimeru/graph.py` の `combine_requests` が決め、本文だけの判断より低い行き先にはなりません。組み合わせで通知も人も無い行き先になったときは、通知を付けます（`asks_guard`）。承認の投稿・詳細・通知の「（ほかに依頼 N 件）」は、記録に残る件数から作ります
- 全文を読んで判断し直した件（1 回目はプレビュー、2 回目は全文）は、`perf` に、2 回の合計を残します
- 測る: `python eval/measure_speed.py --backend kev [--repeat N]`（`sequential` / `lean` / `batch` の 3 通りを、呼び出し・質問・秒数・最終的な行動の違いの表で比べます）。この PC で Kev が起動しているかを先に確かめ、起動していなければ（または接続先がこの PC でなければ）、1 行の案内を出して終わります。Jev は受け付けません（性能の数値は公開できません）

### 判断の正誤の確認と係数の調整

自分の業務の判断で、kimeru の判断が合っているかを測り、係数を調整します。**判断モデルは呼びません。Teams も使いません。** 手順は [1 週間の試し方](trial-week.md)。

- `kimeru review [--limit N]`: 自動で決まった判断を 1 件ずつ、端末で「合っている / 違う / 分からない」と答えます。違うときは、どの質問の答えが違い、正しい答えは何かを選びます。結果は、状態フォルダの `reviews.jsonl`（正誤と、その判断をした判断モデルの名前）と `fixtures_user.jsonl`（`eval/fixtures.jsonl` と同じ形の評価用の例。score の正解は、幅で持ちます）に残ります。元のイベントは、`decisions.jsonl` にあるとおり（既定は要約の長さ。長い依頼の全文を例に残すには、設定 `record_event_full=1`）
- Teams の返信での正誤（設定 `KIMERU_LEARN=1`）: `違う N` は #N の最終結果が違ったという印です。`違う N k` は、直前の `詳細 N` に番号で示した「迷った質問」の k 番が正しい答えだったという印です。どちらも `kimeru review` と同じ `reviews.jsonl`・`fixtures_user.jsonl` に残り、`kimeru calibrate` が読みます。件の状態・投稿・承認・実行は変わりません。出力先の `labels.log.jsonl` には、鍵・正誤・k・時刻だけを残します（返信の文字は残しません）。
- 朝の確認の札（設定 `KIMERU_SPOT_CHECK_PER_DAY=1` 以上）: 朝のまとめの後に、その日の自動の判断から K 件を選び、自分とのチャットに確認の札 `[kimeru 確認 S<k>]` を 1 件ずつ出します（規則だけの判断・オフラインの stub・確認待ちの件・判断済みの件は選びません。直近 24 時間）。`正しい S<k>` は判断が合っていたという正誤、`違う S<k>` は最終結果が違ったという正誤で、どちらも `kimeru review` と同じ `reviews.jsonl`・`fixtures_user.jsonl` に残ります（`違う S<k>` は `違う N` と同じ「誤り」の意味）。札の番号 S<k> は承認の `#N` と別です。`OK` / `NG` は札に効かず、承認・実行・投稿の状態は変わりません。札と答えは `out/spot.json` に 3 日残ります。札への答えを待つあいだ（確かめられなかった `unknown` の札も、3 日の期限まで）は、サイクルごとに自分とのチャットを読みます。待つ札が無いときは読みません。
- `kimeru digest --week [--share]`: 直近 7 日の件数、自動と人の割合、規則で決めた件数、重大な通知、承認の結果、同じ修正指示の繰り返し（別の項目で）、判断の一致率。前の 7 日との比較、種類別の届いた件数、1 件あたりの返信、自動で決めた判断に「違う」が付いた件、提案が一度も変わらなかった OK（下書きのある項目だけ）、投稿から OK を見るまでの中央値（今週と前の 7 日）、calibrate の正誤の残り問数も出します。週の 6 行（到着から判断完了・承認まで、OK の後の送信、正誤のラベルの増分、採用した学習の前後、朝のまとめの上位 3 件の返信・作業）も出します（件数・時間・割合だけ。Jev と判断モデルが分からない判断は数えません）。性能の行（「違う」・変わらなかった OK・中央値）は、Jev の判断と判断モデルが分からない判断を分母分子から外し、その件数を出します。測れた件数が 1〜4 件のものは「参考」、0 件のものは「不明」です。`--share` は、Issue に貼れる形です（数値と環境だけ。同梱のグラフ以外の名前は「追加のグラフ N」に伏せ、本文・人名・件名・ID・パスは出ません）。**一致率は、Jev の判断を数えません**（期間や出力先が違っても）。Jev の性能の数値は、公開できません（TypeSafe の利用規約）
  - 週のまとめには、下書きの使われ方（決まった下書きの件のうち OK・NG・修正の件数と率）と、確認待ちの古さ（投稿からの経過の中央値と最長）も出ます。数値だけで、下書きの本文は出しません（既定で表示）。writer の呼び出し回数と合計秒数（その週の日ごとの記録の合計。状態フォルダの `writer_calls.json`）も 1 行出ます。
- `kimeru config show --share`: Issue に貼れる設定の一覧です。パス、ADO の組織とプロジェクト、サブスクリプション、メールの宛先、接続先の URL は出さず、「設定あり」とだけ出します。1 行目に、kimeru の版、OS、Python、画面の倍率が出ます。不具合の報告には、`config show` ではなく、これを貼ってください
- `kimeru attention list` / `kimeru attention remove NAME`（設定 `interrupt=sittings` のとき）: 待たせている件に続き（改訂が上がる返信。お礼や了解は含まない）が届いて、最初の準備の時刻から 30 分以上たっていたか、「まだ」「返事」などの催促の語があったとき、その送信者を `out/attention.json` に入れます。入った送信者の件は、次のまとめの時刻を待たず、すぐ知らせます。`list` は入っている送信者と理由を読むだけ、`remove NAME` は 1 人を外して `.bak` も消します。朝のまとめに「今後 X さんはすぐ知らせます」と出ます。`digest --week` は承認が多かった時刻から `sit_hours` の候補を 1 行出します（`--share` には出さず、設定は変えません）。既定の `interrupt=all` では何も書かず、何も出しません（[SECURITY.md](../SECURITY.md)）。
- `kimeru learn list | revert L<n>`（設定 `learn=1`）: 正誤を 30 問以上付けた質問ごとに、人に回す向きの変更（確信の基準を上げる、または判断に迷う幅を広げる）だけの提案を、承認の札（`[kimeru #N] 学習の提案`）で出します。札を OK と返すと、その質問の基準だけが変わります（状態フォルダの `thresholds.json` の `nodes`）。探した側で確信して間違える件数が減り、確かめた側で増えないものだけを出し、1 週間に最大 2 件、待っている札がある間は出しません。NG なら 28 日は同じ質問を出しません。グラフ・処理済みの記録・判断の記録は変わりません。`list` は待っている札と採用の記録、`revert L<n>` は 1 件の採用を元に戻します（履歴の行は残ります。同じ質問に後の採用があるあいだは戻さず、新しいものから順に戻します）。札の数と正誤の内訳は、Jev の判断では出しません。
- `不要 N`（設定 `learn=1`）: 議事録の行への NG と同じく却下し、「見る必要はなかった」の印を付けます。同じ一文（議事録の最初の文）の `不要` が 2 日にわたり 3 回・OK 0 のとき、その一文の規則の札を 1 日 1 件出します。OK で `learned_rules.json` に規則（`A<n>`）が入り、同じ一文で種類が決まらない議事録の行は、確かめず記録だけにします（投稿・ADO の起票は増えません）。`kimeru learn revert A<n>` で止められます。規則が止まるのは、この取り消し、後の回に届いた同じ会議（議事録の題名）の 24 時間以内の新しい行（同じ回の箇条書きは数えません）、60 日使わなかったときです。止めた・取り消した一文は、NG と同じく 30 日の間は札を出しません。同じチャットの新しい行で止まる仕組み（chat_id）は、規則を作れる件が議事録だけなので、今は使われません。規則を止めた新しい行は、判断によらず PM へ回します（`[kimeru #N]（規則を戻しました）`）。朝のまとめに「規則で記録だけにした件」を最大 5 行出します。
- 書き方の好み（設定 `learn=1`）: 同じ `修正 N <指示>` の言い方が 30 日以内に別の件でも使われたとき、その言い方を書き方の好みとして OK するかを札で聞きます（`[kimeru #N] 学習の提案: 書き方の好みを下書きに入れますか`）。OK で、以降の `copilot`・`claude`・`grok`・`cmd` の依頼文に、事実を足さない書き方の好みとして入ります（`m365`・`m365-auto`・`codex` には入りません）。好みは `kimeru learn list` に出ます。取り消しは `kimeru learn revert S<sig>`。NG なら残しません。
- `kimeru calibrate [--apply | --revert | --allow-wider] [--min-questions N]`: 記録した回答を、別の係数で読み直して、`conf_scale` と `noul_scale` の変更を探します（条件は 1 週間の試し方）。**判断モデルごとに分けて**探し、適用します。Jev・Kev・CLM の判断を確かめた記録だけが対象で、stub など判断モデルの分からない記録からは、探さず、適用せず、理由を出します。`--apply` は、状態フォルダの `thresholds.json` に書きます。グラフと `profiles.py` は書き換えません。`--revert` は、判断モデルごとの係数を消します（質問ごとの採用は残ります。下の `kimeru learn`）。
- `kimeru replay [--result DIR]`: `kimeru review` / `違う N` で正誤を付けた事例を、今のグラフで、そのとき記録した回答を使って再生し（モデルは呼びません。何も投稿しません）、前回の最終行動（結果の種類とノード）と今の最終行動が変わった件を一覧にします。正しいと付いた件が変わった数、違うと付いた件が変わった数、間違った質問の正解に合うようになった数も出ます。回答が記録に無い質問（手順の型を選ぶ質問など、一部の回答しか残らないもの）に着いた件は「記録なし」と出して、その件だけ止めます。画面と書き出しは、数字・事例の番号（`user-…`）・ノード名だけで、元のメッセージの本文は出ません。`--out` は読む記録のフォルダ、`--result` は `replay.json` の書き出し先（既定は状態フォルダの `replay`）です。`queue.jsonl`・`notices.jsonl`・`approvals.json` は変わりません。判断モデルが Jev の事例を含むときは、正誤の内訳は出ません（TypeSafe の利用規約）。

### 要件ドラフト

`kimeru requirements build N [--answers PATH] [--force]` は、既存 case `N` から回答・利用可能な材料・source references をローカルの Markdown と JSON に保存します。case の承認状態は問いません。回答 JSON では `must_have`、`optional`、`out_of_scope`、`acceptance_criteria`、`open_questions` の5キーすべてが必須で、それぞれ文字列の配列です。回答がない項目は空配列にし、`Unknown` と追加質問として扱います。モデルに分類させません。通常 build は既存の成果物を上書きしません。

`kimeru requirements approve N` は現在の 2 ファイルの hash を記録します。`kimeru requirements status N` は内容が変更されていない場合だけローカル成果物を approved と表示します。この記録は元 case の承認や外部 write を許可しません。詳細とオフライン walkthrough は [要件ドラフト](requirements.md) を参照してください。

状態フォルダ（`%LOCALAPPDATA%\kimeru`、`KIMERU_STATE_DIR` で変えられます）のファイル:

| ファイル | 中身 |
|---|---|
| `config.json` | 設定ファイル（上の節） |
| `reviews.jsonl` | `kimeru review` の正誤（判断の識別子、正誤、時刻、判断モデルの名前）。本文は入りません |
| `fixtures_user.jsonl` | `kimeru review` で作った評価用の例（元のイベントと、正しい答え）。`python eval/run_eval.py score answers.jsonl --fixtures <このファイル>` で読めます |
| `learned.jsonl` | `kimeru learn` の採用と取り消し（札の番号 L<n>、質問の鍵、前後の基準、採用の時刻。判断モデルが Jev なら件数は入りません）。消しません。取り消しは `kimeru learn revert L<n>` で、行は残ります。自動では消さない |
| `thresholds.json` | `kimeru calibrate --apply` が書いた係数の上書き（判断モデルごと）、と `kimeru learn` で OK した質問ごとの基準（`nodes`）。`eval/` のスクリプトは、既定では読みません（`--user-thresholds` を付けたときだけ読み、出力にそのことを出します） |

### 設定ファイル

秘密でない設定は、状態フォルダの `config.json` に置けます。優先する順番は、**コマンドの引数 > 環境変数 > 設定ファイル > 既定値** です。起動のときに 1 回だけ読みます。

```powershell
python -m kimeru config set writer m365      # 設定ファイルに書く
python -m kimeru --out <出力先> config show   # 項目ごとの今の値と出どころ（arg / env / file / default）
python -m kimeru config unset writer
python -m kimeru config path
```

- API キーとトークンは、設定ファイルに書けません（書くと、使われず、警告が出ます）。`show` は、それらが設定されているかどうかだけを出します
- 設定ファイルが壊れているときは、どこが壊れているかを示して、終了コード 2 で止まります。ただし `config path`、`schedule remove` / `status`、`--help`、`demo --replay` は、壊れていても動きます
- **空の環境変数は、未設定と同じ**です（設定ファイルの値、なければ既定値が使われます）。空にして上書きすることはできません。設定ファイルの空の値も、コマンドラインの空の値も、空白だけの値も同じです。これは、すべての設定で同じです（判断モデルの接続先が空でも、モデル名が空でも、既定値になります。空の接続先が別の接続先に落ちることはありません）
- 選べる値が決まっている項目（`backend`・`writer`・`toast`、0/1 の項目、`brief_hour`）は、`config set` のときと、読むときに検査します。読むときは、まず書き方の違いを直します（大文字・小文字、前後の空白、`on` / `off`、`true` / `false`、`yes` / `no`。`Copilot` は `copilot`、`on` は `1`）。それでも知らない値のとき、**`backend` だけ**は、送り先が変わるので、何が違うかを示して終了コード 2 で止まります（直すための `config` コマンドは動きます）。それ以外の項目は、既定値で続け、理由を `config` の警告（標準エラー）と `daily.log.jsonl`（`warnings`）に残します。自動運転は止まりません
- 引数は、省略形（`--back`）を受け付けません（設定に届かないため）。正式な名前で書きます
- Kev と CLM の接続先（`kev_url`・`clm_url`）は、この PC（`127.0.0.1`、`localhost`、`::1`）だけです。ほかのアドレスは、判断の本文が PC の外へ出るので、`kev_url_remote_ok=1`（CLM は `clm_url_remote_ok=1`）を明示しない限り、理由を示して止まります
- `config set push_webhook_body @ファイル名` は、ファイルの中身（JSON）を本文の形として書きます。JSON として正しくないと、書きません。設定ファイルを手で編集して、`{...}` を足さないでください（JSON が 2 つになって、すべてのコマンドが止まります）
- `config set` / `unset` は、ファイルにある、この版が知らない項目を残します。秘密のような名前の項目は、`set` はできませんが、`unset` で消せます
- `daily.log.jsonl` は 256KB を超えると、新しい半分だけに切り詰めます。`schedule status` は末尾だけを読みます
- `schedule install` は、そのとき効いている設定を設定ファイルに保存し、起動行に判断モデルの種類（`--backend stub` も）を必ず付けます。ユーザー環境変数の `KIMERU_BACKEND` があっても、自動運転の判断モデルは変わりません。自動運転は、シェルの設定を引き継がないので、この保存が引き継ぎです。タスクの「前回の結果」には、`daily` の終了コードが出ます
- `daily` は、サイクルごとに、効いている設定の名前と出どころを `daily.log.jsonl` に残します（値は、writer・通知など秘密でないものだけ）。writer が未設定のときは、定型文で動くことも残します
- 自動運転が設定を引き継いだかは、1 サイクルあとに `python -m kimeru --out <出力先> schedule status` で確かめます（最後のサイクルの時刻、失敗した手順、判断待ちの件数、設定の出どころ）

### 環境変数

| 変数 | 意味 |
|---|---|
| `KIMERU_BACKEND` | 既定の判断モデル（`stub` / `jev` / `kev` / `clm`〔試験用〕。未設定なら `stub` = キーワードの簡易判定） |
| `KEV_API_KEY` / `CLM_API_KEY` | Kev / CLM に鍵が要るときのキー（**秘密**: 環境変数だけ。表示には、あるかどうかだけ） |
| `KIMERU_PRIORITY` | 判断の順番（種類のコンマ区切り。既定 `monitor.alert,teams.chat,ado.workitem.created,meeting.item`） |
| `KIMERU_CYCLE_BUDGET` | 1 サイクルの時間の上限（秒。未設定は自動運転の間隔） |
| `KIMERU_PLAN_LEAN` / `KIMERU_BATCH` | 不要な手順の期限を聞かない（既定 0）／グラフの質問を 1 回にまとめる（既定 0） |
| `KIMERU_DRAFT_EXPIRE_HOURS` | 下書きだけを待つ件（`文面だけ確認`。判断が必要な件・重大な件・保留・ADO へ書く／Teams へ返す実行を伴う件は対象外）を、投稿から何時間たったら「期限切れ」で閉じるか（既定 0 = 閉じない）。期限切れは承認でも却下でもなく、閉じた件への `OK N` などは何も実行しない。週のまとめの承認の結果に「期限切れ N」と数え、日次の周期（`--send`）で閉じる |
| `KIMERU_HOLD_STALE_DAYS` | 日付のない保留（`保留 N`）を、朝のまとめで「長く保留: #N（N 日）」と書くまでの日数（既定 0 = 書かない）。1 以上のとき、その日数より長く保留している件だけ書きます。`保留 N <いつ>` の件（`保留 #N（10/15 に再表示）`）には関係しません |
| `KIMERU_LEARN` | Teams の返信 `違う N` / `違う N k` を正誤として記録し、`不要 N` を議事録の言い回しの規則の札にし、`詳細 N` に「迷った質問」の番号を付ける。正誤がたまると、1 週間に最大 2 件、「確信の基準を上げる」提案を承認の札で出します（`kimeru learn`。OK のときだけ、その質問の基準が変わります）。同じ `修正 N` の言い方が別の件でも使われたら、その言い方を書き方の好みとして札で聞き、OK のときだけ CLI writer の依頼文に入ります（`kimeru learn revert S<sig>` で戻す）（既定 0。0 のときは、この返信に反応せず、投稿の文も変わりません） |
| `KIMERU_POST_REASON` | `1` で、承認の投稿の `→` の次と `詳細 N` の先頭に、「迷った点」の 1 行を足す（判断モデルが迷った問いの名前と近い選択肢。規則で人へ回った件は、その規則。`詳細 N` の先頭には、規則が読んだ語（当たった語・拒否した語・人へ回した語、各 20 字まで。最大 3 行）も足す。既定 0。0 のときは投稿・詳細の文が変わりません）。承認の投稿の「迷った点」の行には、メモに足りない材料があればそれを同じ行に足します（確率の数値は出しません） |

| `KIMERU_OWED_KEEP_DAYS` | `KIMERU_SENT_WATCH=1` のときだけ働く、返事の借り（自分がまだ返事を返していない件）を開いたままにする日数（既定 5。1 以上の整数。それ以外の値は 5 として扱う）。朝のまとめの「返事を待っている人」（最大 5 件、残りは「ほか N 件」。`ask_pm` は雑談も入るため名前を出さない）と `kimeru owed` は、この日数の間の件だけを出し、過ぎた件は期限切れとして閉じる。閉じた件（自分のメッセージが相手のチャットの一覧に出た `own_preview`・NG `ng`・済 `done`・期限 `expired`）は `out/owed.jsonl` に、チャットの識別子・時刻・閉じ方・件数だけを 90 日残す（本文と名前は残らない）。`KIMERU_SENT_WATCH=0`（既定）では何も読まず、何も書かず、朝のまとめも変わらない |
| `KIMERU_IDLE_SEC` | Teams を操作する前に、キーボード・マウスが止まっているべき秒数（既定: `post`・`send` は 3、teams-copilot は 4。`0` で待たない。他のチャットを開いて読む処理には効かず、そちらは `KIMERU_READ_IDLE_SEC`（既定 30）だけで決まる） |
| `KIMERU_STATE_DIR` | （`schedule install` が、設定されていれば自動運転の起動行に引き継ぎます）状態フォルダ（設定ファイル、自分とのチャットの目印、writer の休止の印、診断）。未設定なら `%LOCALAPPDATA%\kimeru` |
| `KIMERU_COPILOT_EXE` / `KIMERU_CLAUDE_EXE` / `KIMERU_CODEX_EXE` / `KIMERU_GROK_EXE` | 各 CLI の場所（PATH に無いとき） |
| `KIMERU_WRITER_CMD` | `KIMERU_WRITER=cmd` のコマンド（プロンプトを標準入力で受け、答えを標準出力へ） |
| `KIMERU_WRITER_NO_REST` / `KIMERU_M365_NO_REST` | `1` で、writer の休止（月間上限・失敗のあと）を無視する（試験用） |

### 入力形式

自動判別: Microsoft Graph `chatMessage`、Azure Monitor 共通アラートスキーマ、Azure DevOps `workitem.created`、議事録 `{title, date, text}` または箇条書きの `.txt`（[docs/minutes-format.md](minutes-format.md)）。

### judge ノード

```json
{"kind": "judge", "question": {"type": "noul|choice|score", "instructions": "...", "criteria": "..."}, "routes": {"unsure": "..."}}
```

- noul: `yes` / `no` / `unsure`。`yes_at`（既定 0.7）、`no_at`（既定 0.3）
- choice: 各選択肢 + `unsure`。`min_conf`（既定 0.6）未満は unsure
- score: `bands: [[上限(未満), node], ...]` + `unsure`。`guards` で「Sev0/1 なのに低い評価」を人へ回せる
- 判断モデルの答えが壊れている（型が違う、選択肢に無い、確率が範囲外）ときも `unsure` の行き先へ進む。取り込んだファイルごと止まることはない
- `unsure` の行き先は 3 通り: 人に回す（`advise`。確認待ちに入る）／次の質問へ／安全側の決定（`decide`。`notify: true` なら **[kimeru 通知]**、無ければ記録だけ）。同梱のグラフには、安全側の決定に直結する `unsure` があり、そのうち通知しないものもある（`python -m kimeru validate` の出力ではなく、各グラフの `routes.unsure` で確かめる）

### グラフ全体の重大事象の守り（`severe`）

```json
{"severe": {"field": "severity", "pattern": "^Sev[01]$", "exempt": ["log_resolved"]}}
```

イベントの欄が `pattern` に当たると、`exempt` 以外のどの行き先でも PM に届く。`decide` は通知し（`notify`）、`advise` は確認待ちに入れる。判断モデルがどう答えても変わらない。同梱のグラフでは、アラートの Sev0/1（解消済みは除く）と、優先度 1 で起票された ADO の件に掛けている。

### match ノード（規則）

```json
{"kind": "match", "fields": ["title", "description"], "patterns": ["..."], "exclude": ["テスト環境"], "mixed_if": ["本番"], "routes": {"yes": "...", "no": "...", "mixed": "..."}}
```

正規表現で判定（NFKC 正規化・大文字小文字無視）。`exclude` は同じ欄の一致だけを取り消し、同じ欄に `mixed_if` もあれば `mixed`（人へ）。

- `"exclude_scope": "sentence"` を付けると、`patterns`・`exclude`・`mixed_if` を 1 文ずつ判定します（文は `.` `!` `?` `。` `！` `？` `;` `；` 改行で終わり、終わりの記号は文に残るので、疑問文を `[?？]` で除外できます）。別の文の質問・予定・「if」が、いま起きている障害の文を取り消しません。Teams の `critical_incident`、アラートの `critical_outage` が使います
- `"mixed_field"` は、一致が残ったあとに欄全体で判定します。当たれば `mixed`（人へ）。Teams の `critical_incident` は、別の文の復旧の連絡（「…通りません。復旧しました。」）をこれで人に回します
- `exclude_sentence` は、一致した文に当たったときだけその一致を取り消し、行き先は `no`（モデルに任せる）です。`mixed` にはなりません。ADO の `critical_bug` が、改善・設計・手順書・FAQ・振り返り・要望の文が故障の言葉を含むだけの起票を、P1 にしないために使います
- `when`（`{欄: 正規表現}`）は、規則が当たる対象を絞ります。欄が合わない事象は `no` です。ADO の `critical_bug` は `when` で種別を見て、Bug / Issue / Incident / Defect など故障を表す種別、または種別が無い起票だけを対象にします。Epic・Feature・Task・Test Case・User Story などは規則では P1 にせず、準備の確認へ進みます（Epic と Feature は次の項のとおり記録だけ）
- `critical_bug` は、題名・説明・再現手順・`Severity`（`Microsoft.VSTS.Common.Severity`。`pull ado` が取り込みます）を見ます。`1 - Critical` は規則で P1 です。動詞は「できない」「クラッシュする」のように言い切りの形に限り、英語は単語境界で判定します（「クラッシュレポート」「Crashlytics」「強制終了ボタン」は当たりません）。モデルに任せるのは、データ不整合、脆弱性の報告、範囲や「いま」が書かれていない「画面が真っ白」などです
- 準備の確認（`has_ac` / `has_repro`）の前に、ADO の HTML を整えます。`</div>` `</p>` `</li>` `<br>` は改行、`<ol>` は番号付き、`<style>` `<script>` コメント（Word の貼り付け）は捨て、実体参照を戻し、ゼロ幅の文字を取ります。そのうえで、見出しだけの行（再現手順: 期待結果: 実際の結果: 受け入れ条件: Given / When / Then 前提条件: 手順: Steps to reproduce: Expected: Actual: Acceptance criteria:）と空の箇条書きを消すので、書かれていないテンプレートは空として扱われます。見出しの下に中身があれば「期待結果: 中身」の形で残ります。`has_repro` は、「再現手順: …」、番号付きの手順（1. と 2.）、「期待結果: …」、期待と実際の対だけを準備ができているとみなし、「再現性は不明」「期待しています」だけでは当たりません。Test Case の手順（`Microsoft.VSTS.TCM.Steps`。`pull ado` が取り込み、操作と期待結果を `1. 操作 -> 期待結果` の行にします）が 1 つでも書かれていれば、`has_steps` が準備ができているとみなします（手順の欄は Test Case のときだけ事象に入ります）
- 判断モデルへ渡す ADO の説明・再現手順・受け入れ条件も `judge_text_max` で切ります（規則と writer は全文を見ます）

### plan ノード

`playbooks/*.json` の型を選び、手順ごとの要否・最初の一手・期限（今日 / 今週 / 次スプリント以降）を 1 回のバッチで聞く。終端の `per_step` で手順ごとのアクションを作れる。

### decide ノードの `notify`

`"notify": true` を付けた decide ノード（当番呼び出し・P1・今日中の判断など）は、承認が要らない場合でも `[kimeru 通知]` として自分とのチャットに 1 回投稿されます（writer が文面を書いた件は、承認待ちとして届きます）。

### 評価

```bash
python eval/run_eval.py live --backend kev --out answers.jsonl        # 判断ポイントごと
python eval/e2e.py --backend kev [--fixtures fixtures_holdout.jsonl]  # 最終的な行動
python eval/drafts.py --backend stub --writer copilot                 # 文面の下書きの点検
python eval/day_run.py --backend kev                 # PM の 1 日を、Teams だけ偽物にして通す
python eval/run_eval.py score answers.jsonl --fixtures <状態フォルダ>\fixtures_user.jsonl   # 自分で確かめた判断で採点する（tune も同じ）
```

`eval/` のスクリプトは、`kimeru calibrate --apply` が状態フォルダに書いた係数を、既定では読みません（数値が、その PC の状態で変わらないように）。読むのは `--user-thresholds` を付けたときだけで、出力にそのことが出ます。



| 入力 | グラフ | 判断ポイント | 行き先 |
|---|---|---|---|
| 💬 Teams チャット | `teams_chat.json` | **重大障害（規則）** → **お礼・了解だけか（規則）** → 意図 → 進め方 / 判断期限 | 受領返信・手順ごとの Task・Bug 化・人の確認 |
| 🚨 監視アラート | `monitor_alert.json` | 解消済み → **重大障害（規則）** → 将来のリスクか → 時期 / 顧客影響（**Sev0/1 ガード**）→ ノイズか | 当番呼び出し・予防 Task・P1 Bug・閾値見直し |
| 🎫 ADO チケット | `ado_workitem.json` | **重大バグ（規則）** → Epic / Feature は記録のみ（規則）→ 受け入れ条件・再現手順・テスト手順（規則）→ 着手可能か → 優先度 | P1 固定・情報不足コメント・優先度設定・人のトリアージ |

`KIMERU_LINK_RELATED=1`（既定 0）のときは、この表の入力どうしを結ぶ表示が付きます（Teams の `#N` と ADO の件、同じ規則のアラート、同じ議事録の項目。判断・行き先は変えません。結ぶのは記録にある件だけ）。

Teams のチャットは、一覧に見えている 1 行（プレビュー）で判断します。お礼・了解・あいさつ・絵文字だけのメッセージ（「了解です、ありがとうございます」「承知しました！」「👍」。グループの「名前: 」や「@名前 さん」の前置きは可）は、規則（`ack_only`）で「返信不要」として記録し、判断モデルに聞かず、PM へも投稿しません。これまでは、Kev が「共有・お礼」と正しく選んでも確信度が 0.2〜0.5 で意図ノードの閾値（0.6）に届かず、「意図が判定できないチャット」として PM に回っていました。それ以外の文（「？」がある、プレビューが「…」で切れている、依頼が続く、障害・本番・至急などの語がある、「よろしくお願いします」だけ）は、これまでどおり重大障害の規則と判断モデルが判断し、迷えば PM へ回します。重大障害の規則が先に動くので、この規則が障害の報告を隠すことはありません。自動で片付いた Teams のチャット（「返信不要」と「状況の確認（返信は送っていません）」）は、朝のまとめに「Teams の自動判断」として、件数とチャットの名前（5 件まで）で出ます。数える範囲は「前回のまとめ以降」です（前回の時刻は `daily_state.json` の `brief_at`。不明なときは直近 24 時間、長くても 7 日まで）。

ADO の判断は次のように PM に届きます。

- 情報不足は、writer や実行の設定に関係なく確認待ちに入ります。writer が無ければ、グラフの定型のコメントを案として出します。定型文は、足りないものを書き分けます: Bug は `request_info`（再現手順と期待結果）、Test Case は `request_info_steps`（テスト手順）、それ以外の Task・User Story・PBI・Issue・種別なしは `request_info_ac`（受け入れ条件）。受け入れ条件の無い Task も、これまでどおり情報の依頼として PM に回ります。writer には、種別（`type`）・起票者・領域・受け入れ条件・再現手順・テスト手順（どれも書かれている分。構造の欄は 600 字まで）も材料として渡します。`OK N` は記録だけです（`execute ado.comment` を有効にしていれば、承認した文面を ADO に書きます）。
- Epic と Feature は優先度を付けず、情報の依頼も出さず、「記録のみ」（`record_only`）で自動で決めます（優先度 1 の起票は、ほかの経路と同じく通知されます）。朝のまとめの「ADO の自動判断」に `記録のみ` として出ます。
- 自動で決めた P2・P3 などは、1 件ずつ投稿しません。朝のまとめに「ADO の自動判断」として、「前回のまとめ以降」（前回が不明なら直近 24 時間）の件数（結果ごと）と、`#番号 [種別] 題名 → P2` の行を 5 件まで出し、残りは「ほか N 件」と数えます。確認待ちや通知になった件は、そちらに出るのでここには入りません。迷って決めた件は、次の項に出ます。
- **迷って自動で決めた件。** 判断モデルが迷った答え（`unsure`）を経て、確認も通知も出さずに自動で決まった結果は、記録（`decisions.jsonl`）に `via_unsure: [ノード名]` を残し、朝のまとめに「迷って自動で決めた件（確かめてください）」として、`・ADO #番号 題名 → P3 にした` の形の行を 5 件まで、残りは「ほか N 件」で出します。今すぐの投稿は増やしません。対象は、ノイズか（`noise_check` → 確認タスク）、担当者・期限の有無（`has_owner` / `has_due` → 担当・期限の確認）、計画のリスク（`plan_risk` → リスク登録）、ADO の着手可否（`ready` が迷って優先度の自動設定へ進む経路）など、迷った先が通知も確認待ちも持たない経路すべてです。重大度の高い経路（`severe`）や、迷った先が人への確認・通知の経路は、これまでどおり PM に届くので、この一覧には入りません。
- ADO の承認の投稿と P1 の通知には、作業項目の番号・種別・題名（`title_max` まで）と、`https://dev.azure.com/<組織>/<プロジェクト>/_workitems/edit/<番号>` のリンクが付きます。リンクは、取り込み元（`pull ado`）が記録されている件だけです。起票者や取り込み元の組織・プロジェクトは、承認の投稿への返信 `詳細 N` で見られます。

### 自分とのチャットの投稿の形

- **承認の投稿 `[kimeru #N]`**: 5 行ほど。1 行目 `[kimeru #N] 誰・何の件（40 字まで）`（改訂のあとは `#N] （更新）`）、2 行目 `→ 提案（次の一手）`、設定 `post_reason=1` のときはその次に `迷った点: 問いの名前（近いのは 選択肢）` の 1 行（既定は出ません）、あれば下書き（`案:` 120 字まで。ADO のコメントの実行が有効な件は `コメント:` に書く文面そのもの）、ADO のリンク、最後に `OK N / NG N / 詳細 N`（下書きがあれば `修正 N`、聞き返しの案があれば `聞き返し N` も）。設定 `post_kind_mark=1` のとき、下書きだけを待つ件は 1 行目が `[kimeru #N] 下書き: …` になり、`→` は `文面だけ確認（判断は自動: 提案）` になります（番号の位置は変わりません）。グラフ名・改訂番号・行動の種類名・「判断メモなし」の穴埋めは出しません。`OK` の効果は、ADO のコメントの実行が有効な件にだけ「OK で ADO（組織 / プロジェクト）の #番号 にコメントを書きます」と書きます。無効なら記録だけで、何も書きません。件の続きで出し直したときは、1 行目を最初の依頼のまま（`[kimeru #N] （更新）誰さん: 最初の依頼`）にし、`→` の次に `続き「…」`（30 字まで）を 1 行出します。保留だった件は 1 行目の末尾に `（前回 保留）` を付け、OK か NG で消えます。`詳細 N` の先頭には、設定 `post_reason=1` のとき `規則: 当たった語「…」 / 拒否した語「…」` の行を最大 3 行まで出します（規則が読んだ語の断片、各 20 字まで。記録の経路と同じ規則を同梱のグラフで読み直した結果だけを出し、一致しなければ何も出しません）。`詳細 N` には `最初のメッセージ:` と `続きのメッセージ:` を並べます（最初の依頼は 120 字まで記録します）。
- **`詳細 N`**: 全文を `[kimeru 詳細 #N]` として返します（元のメッセージ・判断メモ・足りない情報・すべての下書き・実行の宛先）。承認ではなく、返信 1 通につき 1 回答えます。承認の投稿でも結果の投稿でもないので、`OK N` などの読み取りには影響しません。
- **`送る N`**（`execute` に `teams.reply` を入れたときだけ）: 承認した返信を、相手の 1 対 1 のチャットへ 1 回送ります。`OK N` だけでは送りません。投稿に出した文面と、同じ文面を送ります。結果は `[kimeru 実行 #N k]` で返します。`--send` を付けない実行で返したときは、次の `--send` の実行で送ります。承認から 48 時間のあいだだけ読みます（それより後の `送る N` は、ほかの理由で読まれたときでも送らず、何も返しません）。`送る #N` も可。
- **通知 `[kimeru 通知]`**: 4 行まで。何の件か、`→` 何を決めて何を記録したか、あれば ADO のリンク。返信は要りません。
- 返信を受け付けた確認は PC の通知だけで、自分とのチャットには投稿しません（1 回のサイクルの結果の投稿は、番号ごとに 1 通です）。

`decide` ノードに `"queue": true` を付けると、自動で決めたうえで、確認待ちにも入ります（`request_info` が使っています）。
| 📝 議事録 | `meeting_item.json` | ラベル（`決定:` `タスク:` `リスク:` `共有:`）は規則、なければ行の種類 → 担当 → 期限 | 決定ログ・Task・Risk 登録と対策手順 |

進め方の型（`playbooks/`、9 種類）: スケジュール変更 / 障害対応 / スコープ変更 / 人員調整 / リリース判定 / ステークホルダー対応 / リスク対応 / 要件明確化 / 要件の検討。

グラフも型も JSON なので、**自分のチームの判断ポイントを足せます**。閉路・到達不能ノード・ルート漏れ・不正なしきい値は `python -m kimeru validate` が弾きます。質問の書き方は警告として `warn` 行に出ます（落としません。グラフは変わりません）: `noul` の文に `and`・`or`・`または`・`かつ`（条件を二つ聞いている）、`none` の選択肢の無い `choice`、程度語だけの `score` の水準（`Low` など。状況で書く）。
