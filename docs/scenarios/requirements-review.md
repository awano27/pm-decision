# シナリオ: 「新機能の要件を検討してもらえますか」と頼まれたとき

これは会話形式で不足情報を尋ねる判断シナリオです。既存 case からファイルを作る `requirements build` とは別の機能です。Markdown/JSON の要件ドラフトと hash 承認は [要件ドラフト](../requirements.md) を参照してください。

営業から、新しい機能の要件を検討してほしいという依頼が届きます。PM が「決める」のではなく「一緒に組み立てる」種類の依頼です。
kimeru がどう受け止め、自分とのチャットに何が届き（スマホの Teams でも読めます。スマホへの通知はありません）、返信でどう進むかを、実際の出力で示します。

> 人名・機能名・日付はすべて架空です。判断は Kev（PC の中で動く判断モデル）、文面は GPT（`KIMERU_WRITER=codex`）の実際の出力から取っています（コミット bcfce54 の時点の出力です。現在の版では Codex writer は起動せず定型文になるため、同じ文面は再現できません）。
> `examples/teams_requirements.json` と `examples/teams_requirements_vague.json` で再現できます。

## 1. 届いた依頼

> **Nakamura（営業）**: 予約リマインド通知の要件を検討してもらえますか。営業が大手の顧客に提案したくて、来月の顧客説明までに叩き台がほしいです

あなたは別の会議中です。

## 2. kimeru が裏でやること（PC の中だけ）

1. **判断（Kev）**: 「これは、決めごとでも、進捗の質問でも、障害でもなく、**要件の検討の依頼**」と読み取ります。
2. **進め方を組み立てる**: 「要件の検討」の型（下の 6 ステップ）から、この依頼に要るものを選び、期限の目安をつけます。
3. **文面とメモを下書き**: 返信、聞き返し、作業項目の説明、判断メモ。この種類の依頼では、材料に無い **目的・対象ユーザー** を、依頼元に聞く形で書きます。
4. **自分とのチャットに投稿**: 承認するまで、何も外へ出ません。

要件の検討の型（`playbooks/requirements_review.json`）:

| | ステップ |
|---|---|
| 1 | 目的・解決したい課題・対象ユーザーを依頼元に確認 |
| 2 | 現状の機能と制約（依存・期限・予算）を整理 ※期限・顧客・他チームが出てくるときだけ |
| 3 | 要件の叩き台（必須・あると良い・対象外）を作成 |
| 4 | 受け入れ条件と非機能要件（性能・セキュリティ・運用）を追記 |
| 5 | 依頼元・開発・QA で要件をレビュー ※複数のチームが関わるときだけ |
| 6 | 合意した要件をチケットに登録し、見積りを依頼 |

## 3. 自分とのチャットに届くもの（スマホの Teams で読める）

会議の合間に、次の投稿が読めます（実際の出力。長い行は省略しています）。

```
[kimeru #41] 判断が必要（teams-chat-triage）
内容: 要件の検討: 1.目的・解決したい課題・対象ユーザーを依頼元に確認（今日（目安））
      → 2.現状の機能と制約（依存・期限・予算）を整理 → 3.要件の叩き台を作成 → …
承認で実行: teams.reply, ado.create ×5
元: Nakamura: 予約リマインド通知の要件を検討してもらえますか。…

Copilot のメモ:
・要点: 予約リマインド通知について、来月の顧客説明に向けた要件の叩き台が求められています。
・足りない情報: 解決したい課題と目的 / 対象ユーザー / 現状機能・依存関係・期限・予算、および成功の基準
・選択肢:
   案：最小の機能から始める／範囲を絞って検討しやすい／顧客説明に必要な内容を満たすか確認が必要
   案：一式で作る／全体像を提示しやすい／必要性や制約が未確認のまま範囲が広がる懸念
   案：既存機能の拡張で対応する／現状機能を活用できる可能性がある／拡張できるか依存関係の確認が必要
・次の一手: Nakamuraさんに目的と対象ユーザーを確認し、現状機能と制約を整理します。

返信の下書き:
Nakamuraさん、予約リマインド通知の要件検討について承知しました。来月の顧客説明に向けて
叩き台を作るため、まず解決したい課題と対象ユーザーを教えていただけますか。

作業項目「目的・解決したい課題・対象ユーザーを依頼元に確認」の説明:
予約リマインド通知で解決したい課題と、利用する対象ユーザーを確認します。
確認した内容を質問リストにまとめます。

返信: OK 41 / NG 41 / 保留 41 / 修正 41 <直してほしい点> / 聞き返し 41
```

読んでわかること:

- **何を頼まれたか**が 1 文で分かります（要点）。
- **決める前に足りないもの**（目的・対象・制約・成功の基準）が、先に整理されています。
- 要件の切り方の **選択肢と、それぞれの利点・懸念** が出ています（最小から始める／一式／既存の拡張）。
- 返信の下書きは、依頼の言葉（「来月の顧客説明」）を使い、**材料に無い期限や約束を作らず**、聞くべきことを 2 つに絞っています。

## 4. あなたの返信（会議を抜けずに）

| 返信 | 何が起きるか |
|---|---|
| `OK 41` | 承認。返信の文面と 5 件の作業項目を、実行の計画として記録します（v1.0 は記録のみ。文面はコピーして送ります） |
| `修正 41 もっと短く` | 指示どおりに書き直して、同じ番号 `#41` で投稿し直します |
| `聞き返し 41` | 「予約リマインド通知で解決したい課題と、利用する対象ユーザーを教えていただけますか。」という、聞き返しだけの文面に差し替えます |
| `保留 41` / `NG 41` | 保留にする／却下する |

## 5. 少し曖昧な依頼（別の例）

> **Ogawa**: ログイン画面の SSO 対応、どこまでやるかまだ固まっていなくて。要件を整理してもらえると助かります

同じ型（要件の検討）で進み、投稿は次のようになります。

- 要点: Ogawaさんは、ログイン画面の SSO 対応について要件の整理を求めています。
- 足りない情報: 解決したい課題・目的 / 対象ユーザー / 制約と成功の基準
- 返信の下書き: 「Ogawaさん、ログイン画面の SSO 対応について承知しました。まず要件の叩き台を作成します。目的や解決したい課題と、対象ユーザーを教えていただけますか。」
- 作業項目の説明: 「…回答をまとめた質問リストができたら完了です。」「…要件の叩き台ができたら完了です。」（完了を **成果物** で書きます）

## 6. 似ているけれど、別扱いになる依頼

「要件」という言葉が入っていても、次のものは要件の検討にはしません（判断モデルが意味で読み分けます）。

| 届いたメッセージ | 扱い |
|---|---|
| 「その新機能、今スプリントに入れてよいか判断お願いします」 | 判断の依頼（決めるのはあなた） |
| 「要件定義の進捗はどうなっていますか」 | 進捗の質問 |
| 「要件定義書を共有します。ご確認ください」 | 情報共有（迷うときは、あなたに確認） |

迷ったときは、勝手に進めず、あなたの確認待ちに回ります。

## 7. 確かめたこと・限界

- 判断（Kev）が、この依頼を要件の検討として読み取れるかを、架空の文例で確かめました。
  - **調整に使った 10 件**（要件の検討 6 件、紛らわしい 4 件）: 9 件が意図どおり。残る 1 件（「要件定義書を共有します」）は、あなたの確認待ちになりました。誤った扱いは 0 件です。
  - **調整に使っていない新しい 10 件**（別の分野・言い回しの要件の検討 6 件、紛らわしい 4 件）: **10 件すべて意図どおり**でした（紛らわしい 4 件は、判断・進捗の質問・情報共有・障害として扱われました）。
  - 既存の Teams の依頼（開発用 28 件、検証用 20 件）でも、誤った扱いは 0 件のままで、正しく扱えた件数は減りませんでした（14→16 件、15→17 件）。
  - いずれも作者が作った架空の文例での数字で、件数も少ないので、実際の業務のメッセージでの精度は分かりません。
- **kimeru は、要件の叩き台そのものは書きません。** v1.0 の役割は、「何を聞くか」「どの順に進めるか」「返信の下書き」を整えるところまでです。依頼元の回答が返ってきたあとの叩き台づくりは、あなたの作業です。
- v1.0 では、返信や起票は **実行せず記録のみ** です。
- 判断が要件の検討と読み取れない依頼は、これまでどおり「意図が判定できない」として、あなたに確認します。

## 8. 次に足せそうなもの

- 依頼元の回答が返ってきたら、それを材料に、**要件の叩き台の下書き**（必須・あると良い・対象外、受け入れ条件）を作る。
- 同じ機能の依頼が複数の人から来たとき、まとめて 1 件にする。
- ADO のチケットとして起票された「要件検討」にも、同じ型を使う。
