# 1 週間の試し方

最初の試行では対象 ADO プロジェクトを 1 つに絞り、情報不足の確認依頼を扱います。導入前後の作業時間、下書きの利用状況、通知を本人が受け取ったか、作業を手動で完了したかを別々に記録します。1 週間は任意の観察期間で、改善や精度を約束するものではありません。追加シナリオを試す場合は pilot の結果と分けてください。**trial 集計は本文を共有しません**が、通常の case / `out` のファイルには本文が含まれる場合があります。

通知受理は端末受信の証拠ではなく、端末受信も case 完了の証拠ではありません。これらは本人の確認を別々に記録してください。[要件ドラフト](requirements.md) は case の材料を明示的にローカルへ永続保存するので、作成前に保存先を確認します。

## この試行で分かること・分からないこと

- **分かること**: あなたの環境で、README だけで最初の成功に届くか。承認の流れが回るか。同じ種類の確認作業の正味の時間が、導入の前と後でどう違ったか（あなた 1 人の観察）。
- **分からないこと**: 一般的な精度や時短。1 人・1 週間の結果は観察であり、他の人や他の週には当てはめません。

## 4 つの成功基準と測り方

| 基準 | 何を見るか | 測り方 |
|---|---|---|
| 1. 初回成功 | README だけで、本物の判断（Kev か Jev）で 1 件を判断し、自分とのチャットに確認待ちが届くまで | 始めた時刻と届いた時刻、途中で調べたこと・人に聞いた回数、つまずいた README の見出し名 |
| 2. 理解 | 次の 5 問に、導入の前と 1 週間後に答える（同じ問い）: ①既定で PC の外へ出るものは何か ②`OK N` で何が起きるか（何が起きないか） ③スマホに何が届くか ④記録はどこに、どれだけ残るか ⑤止める・消すには何をするか | 正答数（前 n/5 → 後 n/5）。答えは README と SECURITY.md にある |
| 3. 継続利用 | 5 営業日のうち、自動運転か `daily` が動いた日数と、承認・却下の件数 | `digest --week --share` の出力 |
| 4. 正味の時短 | 同じ種類の確認作業 1 件にかかった、人の作業時間の導入前と導入後 | `trial record --case N --before-minutes B --after-minutes A --draft unchanged|edited|unused --outcome correct|wrong|unknown` |

### 最小件数

- 独立した case が **5 ペア**（導入前と導入後の両方がある case）に満たないと、`trial report` は **inconclusive** と出します。これは仕様です（5 ペア以上でも「記述統計で、因果の証明ではない」と出ます）。
- 導入前（before）の時間は、自動運転を入れる前に、同じ種類の作業を **3 件以上** 自分で測っておきます。

### 正味の時間の数え方

- **含める**: 材料と下書きを読む、直す、行動を選ぶ、承認後の文面をコピーして相手へ送る、失敗したときにやり直す時間。
- **含めない**: 判断モデルや writer の処理を待つ時間、投稿や返信を待つ時間、放置や中断の時間。
- モデルの応答時間は時短ではありません。正味の時間だけで比べます。

## 失敗・手戻り・中止も記録する

うまくいかなかったことも、成功と同じ重さで残します。止まった日、使わなかった下書き、承認を取り消した件、途中でやめた理由（時間・組織のルール・不具合など）を、日付と件数だけで書きます。

## 報告の様式（集計だけ）

本文・氏名・社名・原ログは書きません。次の表の形で、集計だけを [利用結果の報告](https://github.com/awano27/pm-decision/issues/new/choose) に貼ります。

| 項目 | 書くこと |
|---|---|
| 参加者 | 作者本人／第三者（同じ組織の別チーム）／第三者（別の組織） |
| 環境 | `config show --share` の 1 行目、管理された PC か、判断モデル（Kev / Jev / stub）、writer の有無 |
| 初回成功 | かかった分数、人に聞いた回数、つまずいた README の見出し名 |
| 理解 5 問 | 前 n/5 → 後 n/5 |
| 継続 | 動いた日数 / 5、承認 n・却下 n |
| 正味の時間 | ペア数、中央値、範囲（`trial report --share`） |
| 下書き | そのまま使った・直して使った・使わなかった の件数 |
| 失敗・手戻り・中止 | 件数と、日付だけのメモ |
| 公開の許可 | この集計を公開してよいか（はい／いいえ）。「いいえ」なら作者にだけ伝える |

公開してよいと答えた集計だけを、作者が [evaluation.md の「利用者の環境での結果」](evaluation.md#利用者の環境での結果) に載せます。

## 準備（初日、10 分）

```powershell
python -m kimeru config set backend kev          # 判断モデル（Kev を使うとき）
python -m kimeru config set writer m365          # 文面の下書き。使えるものを選ぶ（README の「文面の下書き」）
python -m kimeru --out <出力先> config show       # 効いている設定と、その出どころ
python -m kimeru schedule install                # 5 分ごとの自動運転（設定は設定ファイルで引き継がれる）
```

## 毎日（合計 5 分）

1. Teams の自分とのチャット（PC でも、スマホの Teams でも）で、確認待ちに `OK N` / `NG N` / `保留 N` / `修正 N <指示>` / `聞き返し N` を返す。承認した返信文は自分でコピーして相手へ送る
2. 夕方、PC の端末で、自動で決まった判断を確かめる

```powershell
python -m kimeru review            # 1 件ずつ「合っている / 違う / 分からない」。違うときは、正しい答えを選ぶ（20 件まで。--limit で変える）
```

結果全体が違っていても、誤りを質問単位のラベルにできないときは、確認時に `w`（最終結果が違う）を選びます。これは最終結果の誤りとして記録し、質問単位の正誤ラベルは作りません。

case ごとの before/after の時間と下書き利用状況は手動で計測し、次のローカルコマンドに明示します。これらの値は業務成果の自動測定ではありません。

分数は、材料・下書きを読む、修正する、行動を選ぶという**実作業時間**です。放置や中断の時間、モデル処理秒数、投稿・返信ポーリングの待ち時間と分けて計測してください。before は同じ種類・範囲の確認作業の導入前の観測値です。違う作業を同一ペアにして時間短縮と呼ばないでください。

```powershell
python -m kimeru trial record --case 1 --before-minutes 18 --after-minutes 12 --draft edited --outcome correct
python -m kimeru trial report
```

通知経路の設定状態を読むだけなら `python -m kimeru onboarding status` を使います。通知を送る操作は別の `onboarding notification-test --send` で、送信受理後に端末を本人が確認してから `onboarding confirm TOKEN` を実行します。dry run / status は送信しません。pilot の case を自動的に完了にする機能ではありません。

Teams は使いません。確かめた結果は、状態フォルダの `fixtures_user.jsonl`（評価用の形）と `reviews.jsonl`（正誤と、その判断をした判断モデルの名前）に、PC の中だけで残ります。元のイベントは、既定では要約の長さ（120 文字）までしか記録に残りません。長い依頼の全文を評価用の例に残したいときだけ、`python -m kimeru config set record_event_full 1` にします（記録が、それだけ敏感になります: [SECURITY.md](../SECURITY.md#記録に残る範囲と期間)）。

## 1 週間後

```powershell
python -m kimeru digest --week           # 件数、自動と人の割合、規則で決めた件数、重大な通知、承認の結果、一致率
python -m kimeru digest --week --share   # Issue に貼れる形（数値と環境だけ。追加したグラフの名前は伏せます）
python -m kimeru trial report --share    # 集計のみ。Jev と判断モデル不明の試行は除外
python -m kimeru calibrate               # 係数を調整できるか（モデルは呼びません）
python -m kimeru config show --share     # Issue に貼れる設定の一覧（パス・組織・サブスクリプションは出ません）
```

`trial report --share` は個別 case の計測ペアを出さず、Jev と判断モデルの出所が分からない試行を除いて集計します。導入前の時間が未記録なら、時間差は `Unknown` のままです。承認から引き渡しまでの時間も証拠がない場合は `Unknown` と表示されます。

### 出力で確かめる計測範囲

`out/decisions.jsonl` の `measurement` は schema、出所（`local` / `demo`）、計測用 generation、下書き準備時刻を持ちます。追加情報で既存 case に統合した判断には、元の case と照合する `case_key` が付きます。`approvals.json` と `approvals.log.jsonl` の計測情報には、同じ提案の本文を読み戻せた時刻と `OK` を受け付けた時刻が残ります。後者は外部実行より前の観測です。計測メタデータは承認・送信の条件には使いません。

`python -m kimeru report` が既存の `out/report.html` に表示する Measurement coverage は次を別々に示します。

- 手動の確認分数は `trial.json` の明示観測で、モデル・writer の処理秒数とは別です。
- 下書き採用は利用可能な下書きがある case を対象とし、明示観測した現在の提案の最新記録だけで採用率を計算します。観測済み / 対象 / Unknown と、重複観測数を表示します。修正率は `edited / (unchanged + edited)` です。対象となる下書きが無い件や、古い計測世代の利用状況は採用の分母に混ぜません。
- Draft delivery wait は下書き準備から本文の正の読み戻し確認までです。Observed approval latency はその確認からアプリによる `OK` 受理までで、ポーリング・保留を含みます。Pending age は未承認の開いた区間で、完了した承認待ちとは区別します。
- Event-arrival-to-approval は信頼できる到着時刻がないため **Unknown** です。古い記録・不正・未来・逆転・世代不一致の時刻も推定しません。
- `delivery confirm` は人が確認した時刻・出所を残すだけで、元の投稿時刻を補いません。通知の端末受信、承認、下書き採用、ADO の作業完了はそれぞれ別の証拠です。

HTML の各判断には出所・generation と対応する時刻を示し、ローカルの元記録を追えます。通常の HTML / JSONL には本文が含まれるので共有しないでください。`trial report --share` は本文・名前・URL・パス・case ID を含まない集計のみで、Jev / 判断元不明の計測を除外します。合成 demo の値・試行観測は業務効果として数えません。実利用の時間短縮・採用率・承認待ち短縮は未測定です。

引き渡しの集計は、ブリッジによる画面読み戻しと、本人が「自分とのチャットに表示された」と申告した記録を区別して保存します。どちらも自分とのチャットへの引き渡し確認であり、ADO 側の作業完了の証拠ではありません。

- `calibrate` は、正誤を付けた質問が **100 問** 以上あるときだけ、変更を提案します。足りなければ、足りない数を表示して、何も変えません。
- 提案は、データを 2 つに分け、片方で探し、もう片方で確かめて、確信して間違える件数が増えないときだけ出ます。
- 既定では、**人に回す件数が増える方向（慎重な方向）** の変更だけを提案します。自動で決める範囲を広げる変更は、`--allow-wider` を付けたときだけです。
- 判断モデルが混ざった記録は、判断モデルごとに分けて探します。stub など、判断モデルの分からない記録からは、探さず、適用せず、理由を出します。
- 適用は、あなたが決めます: `python -m kimeru calibrate --apply`。ローカルの上書きファイル（`thresholds.json`）に保存し、グラフと `profiles.py` は書き換えません。戻すには `python -m kimeru calibrate --revert`。

## 結果の報告（任意）

`digest --week --share` の出力を、[利用結果の報告](https://github.com/awano27/pm-decision/issues/new/choose) に貼ってください。本文・人名・件名・ID は出力に含まれません（貼る前に、目で確かめてください）。
判断の一致率は、Jev の判断を数えません（TypeSafe の利用規約: Jev の性能の数値は公開できません）。不具合の報告には、`config show` ではなく `config show --share` の出力を貼ってください（`config show` には、パスや組織の名前が入ります）。

画面操作や通知の環境ごとの結果は、「動作環境の報告」に書けます。
