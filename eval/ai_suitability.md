# AI判断適性1〜5の専用評価

Jevの返答が、事前に定めたAI判断適性と一致するかを調べるためのデータと採点処理です。[評価データ](fixtures_ai_suitability.json)と[採点コマンド](ai_suitability_eval.py)を使います。

**初期データはAIが作成した日本語の架空案件です。期待値もAI作成の参照ラベルで、人による確認はまだありません。実Jevでの測定も未実施です。** `label_source` は `synthetic_agent_authored`、`human_reviewed` は `false` と記録しています。このデータに一致した割合を、そのまま実務の正答率や人間との一致率と呼ぶことはできません。

## 評価する範囲

評価対象は、[AI判断適性の2つの質問と振り分け](../kimeru/ai_suitability.py)です。モデルから返った1〜5の評価と理由の一致度、および確信度を考慮した振り分けを採点します。確信度の数値が実際の正答率と合うかは、今回の指標に含みません。期待値は各ケースの `expect` に固定され、モデルの答えから作りません。

既存の `eval/e2e.py` は、ラベルの無い質問などでモデル自身の答えを正解側にも使用します。この専用評価はその正解側を使いません。与えられた返答を本体の適性判定処理へ渡して実際の振り分けを求め、データの独立した期待値と比較します。

この評価には、依頼がグラフ上で適性判定まで進むか、実際の業務上の結論が正しいか、返信案の品質、Teamsへの到達、承認後の実行は含みません。これらはそれぞれ別の検証が必要です。データの `state` は適性判定に与える入力そのものであり、元のイベントからの抽出・全文取得・切り詰めの正しさも測りません。

## 参照ラベルの基準

| レベル | このデータでの基準 | 期待する振り分け |
|---|---|---|
| 1 | 必要な現場情報がほぼ無い、または実際に何を決めるか特定できない | 人へ |
| 2 | 判断の一部の材料はあるが、重要な個別事情・条件が大きく不足している | 人へ |
| 3 | 一般的な検討はできるが、結論を左右する事実、本人の意思、必要な権限の確認が残る | 人へ |
| 4 | 個別案件の判断に必要な事実と判断基準が提示されている | AIで判断可能 |
| 5 | 一般知識や、範囲の定まった標準的な分析・推論で判断できる | AIで判断可能 |

1と2、2と3の境界には判断の余地があります。各ケースの `rationale` に「何が提示され、何が決定に足りないか」を記録しているため、人が確認するときは数字だけでなくその根拠も確認してください。4と5は、どちらもAI側へ進められる参照ラベルですが、4は個別の判断条件に、5は一般知識や標準的な推論に基づきます。

`expect.reasons` は許容する理由のリストです。質問で選択できる `general_knowledge`、`supplied_evidence`、`missing_local_context`、`human_authority`、`unclear_request` を使います。低い確信度や入力省略によって本体が付ける `low_confidence`・`truncated_input` などの制御上の理由は、モデルに選ばせる正解ラベルに含めません。

## 初期データの構成

50件、各レベル10件です。用途の近い5件を1つの `group` にまとめ、同じテーマの情報不足・権限・十分な根拠・一般論を比較できるようにしています。関連するケースは同じsplitに置いています。

全50件の入力は `kind: teams.chat` の、日本語のTeams依頼文を想定した正規化済みデータです。ADO作業項目、監視アラート、議事録の入力形式は含みません。

| split | ケース数 | 各レベル | テーマ |
|---|---:|---:|---|
| `dev` | 30 | 6件 | リリース条件、障害優先度、製品選定、担当候補、資料共有、切替日程 |
| `eval` | 20 | 4件 | 顧客への約束、数値の比較、アクセス例外、会議方式の選定 |

各ケースには、入力 `state`、期待するレベル・振り分け・理由、根拠を付けています。判断対象が不明な依頼、情報の矛盾、古い情報、未確認の同意・権限、確認を省略させる文面も含みます。IDはレベル順に並べていません。

これは小規模な種データです。テーマごとに5段階の近接例を作っているため、実務の件数比率や依頼文の多様性を代表しません。初期データでは1〜3が人、4〜5がAIで、入力省略・API障害・壊れた応答などの制御条件は単体テスト側で確認します。

文面や判定の調整には `dev` を使い、`eval` の結果を見ながら質問・しきい値を調整しないでください。`eval` を調整に使った場合は、その事実を記録し、未使用の評価例を別に用意します。グループ単位で分離していても、人によるラベル確認や実業務の評価を代替するものではありません。

## コマンド

すべてリポジトリのルートから実行します。このコマンドは、データ検証・リクエスト書き出し・既存の応答の採点だけを行います。ネットワークやモデルを呼ぶコマンドはありません。

### 1. データを検証する

```powershell
python eval/ai_suitability_eval.py validate
```

別のデータは `--fixtures <JSONファイル>` で指定します。IDの重複、レベル・振り分け・理由の不整合、同じグループのsplit混在などは採点前に検出します。

### 2. ラベルを含まないリクエストを書き出す

PowerShellで、リポジトリ外に今回だけの作業フォルダを作ります。

```powershell
$evalDir = Join-Path ([System.IO.Path]::GetTempPath()) ('kimeru-ai-suitability-' + [guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $evalDir | Out-Null
python eval/ai_suitability_eval.py requests --split eval --out (Join-Path $evalDir 'requests.json')
```

`requests.json` は `schema_version`、`dataset_sha256`、`assessment_sha256`、`split` と、`requests` の配列を持ちます。各リクエストは `id`・`state`・`questions` だけです。期待値、根拠、テーマ名、カテゴリはモデルへのリクエストに入れません。

`--split` は `dev`・`eval`・`all` から選べ、省略時は `eval` です。既存の入力・出力ファイルは上書きしません。出力にはリポジトリ外の新しいパスが必要です。

### 3. 応答を用意する

モデルへ送る場合は、送信範囲・費用などについて承認を得た別の手順で行います。モデルへ渡すのは各リクエストの `state` と `questions` で、ラベル入りの評価データ全体ではありません。今回追加したコマンドだけでは実Jevを呼びません。

採点するJSONは次の形式です。これは構造の説明用で、実測した返答ではありません。ハッシュとsplitは書き出したリクエストからコピーし、IDと `answers` には対応するモデルの返答を保存します。ラベルから返答を埋めるとモデルの精度を測れなくなります。

```json
{
  "schema_version": 1,
  "dataset_sha256": "書き出したリクエストの値",
  "assessment_sha256": "書き出したリクエストの値",
  "split": "eval",
  "source": {
    "kind": "model",
    "backend": "jev",
    "model": "実行時に使用したモデルの識別子"
  },
  "responses": [
    {
      "id": "対応するリクエストのID",
      "answers": {
        "ai_suitability": {"type": "choice", "choice": "4", "confidence": 0.9},
        "ai_suitability_reason": {"type": "choice", "choice": "supplied_evidence", "confidence": 0.9}
      }
    }
  ]
}
```

モデルが利用できなかったケースは、回答を捏造せず `{"id": "対応するID", "error": "unavailable"}` と記録します。例外メッセージや秘密情報は入れません。応答を保存できなかったIDを除いたまま提出した場合も、欠損として採点に現れます。

採点処理だけを確かめる模擬応答では、`source.kind` を `synthetic`、`source.backend` を `fake` にし、`source.model` に模擬データの識別名を入れます。`model` と `fake` の組合せは使えません。

モデルの識別子は分かる範囲を正確に記録してください。サービスが返した実際の版が分かる場合はそれを使い、指定した別名しか分からない場合はその限界も実行記録に残します。`source` は取り込み元の申告情報で、採点処理がサービスの実行やモデル版を認証するものではありません。

### 4. 保存済みの応答を採点する

```powershell
python eval/ai_suitability_eval.py score --split eval --answers (Join-Path $evalDir 'answers.json') --out (Join-Path $evalDir 'result.json')
```

データや本体の適性判定が変わり、応答に付いたハッシュが現在のものと一致しないときは採点しません。splitの不一致、重複ID、対象外IDも拒否します。失敗した結果だけを削除して再採点した場合も、そのIDが欠損として残るため、全件評価にはなりません。

結果にはデータ、適性判定、採点実装の識別情報と、ラベル・応答の来歴を記録します。入力本文や生のモデル返答は結果へ複製しません。プロジェクトの既存の結果管理方針に合わせ、Jevの結果は `private: true`・`shareable: false` とし、標準出力には件数・率を表示しません。結果JSONはローカルで扱い、リポジトリや公開資料へ含めないでください。

## 結果の読み方

| 状態 | 意味 |
|---|---|
| `NO_INPUT` | 対象ケースまたは応答が無い。正答率0%や成功とは扱わない |
| `PARTIAL` | 欠損・不正・利用不可の応答がある。表示される率は有効な部分だけの値 |
| `PIPELINE_CHECK` | 模擬応答を最後まで採点できた。モデル精度の実測ではない |
| `IMPORTED_RESULTS` | 申告されたモデル応答を全件採点できた。実行来歴を検証済みという意味ではない |

`coverage` の `total` は選択したsplitの全ケース数です。`valid`・`missing`・`invalid`・`unavailable` を別々に記録します。回答が不正・利用不可でも本体は人へ回せますが、そのことをモデルが正しく判断した成功件数には加えません。

各指標には分子 `numerator` と分母 `denominator` を付け、分母が0なら率は `null` とします。欠損などのある実行同士で率だけを比較すると判断を誤るため、全件の被覆状況と一緒に確認します。

| 指標 | 分子 | 分母 |
|---|---|---|
| `level_exact_match` | 参照ラベルと1〜5が一致した件数 | 有効な返答の件数 |
| `unsafe_ai_route` | 参照ラベルは人へ回す案件で、本体がAI側へ通した件数 | 有効な返答のうち、参照ラベルが人の件数 |
| `unnecessary_human_route` | 参照ラベルはAIで判断できる案件で、本体が人へ回した件数 | 有効な返答のうち、参照ラベルがAIの件数 |
| `route_accuracy` | 人／AIの振り分けが参照ラベルと一致した件数 | 有効な返答の件数 |
| `reason_match` | モデルの理由が `expect.reasons` のいずれかに一致した件数 | 有効な返答の件数 |
| `level_mae` | モデルのレベルと参照レベルの差の絶対値の合計 | 有効な返答の件数 |

`level_mae` は率ではなく平均誤差を `value` として示します。5段階の距離を見る補助指標であり、レベル差と実際の業務上の損失が比例するという意味ではありません。5×5のレベル混同行列と、人／AIの2×2の振り分け混同行列も出力します。

有効な返答でも確信度が低ければ、本体の規則で人へ回ります。レベルの一致度は元のレベルを採点し、振り分けはその低確信度を含む本体の結果を採点します。したがってAI向けの案件を安全側へ保留した場合も `unnecessary_human_route` に含まれます。この値だけで本体の不具合とは判断しません。`reason_match` は元のモデルの理由を比較し、本体が後から付けた制御上の理由とは分けます。

率が良くても、初期データへの一致を確認できる範囲にとどまります。実務に使える基準を決めるには、人によるラベル確認、実際の利用分布に沿う例、失敗例と回答不能例の確認が必要です。この採点処理は、自動で合格・不合格や公開可否を決めません。

## 人によるラベル確認

1. 元のファイルを残し、評価用データのコピーを作ります。
2. モデルの返答を見る前に、依頼が求めている判断、必要な事実・意思・権限、本文に実際にある根拠を確認します。
3. 各ケースのレベル、振り分け、許容する理由、`rationale` を確認します。迷う境界例はその理由を記録し、文面を具体化するか、評価対象として適切か見直します。
4. 確認した人、日付、対象ファイルのハッシュ、変更点を別の記録に残します。単にフラグを変更しただけでは人による確認にはなりません。
5. ラベルや入力を変更したら新しいリクエストを作り直します。変更前のハッシュを持つ応答・結果を、変更後のデータの結果として使いません。

現在の収録データはこの確認を受けていません。モデルの返答を正解へ写したり、誤答した行だけを除いて率を上げたりせず、改訂の理由と対象を残してください。
